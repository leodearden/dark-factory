# Deliberation — from committed report to filed program

Phase 6 of `/review-all`. The run ends at the report; this protocol turns its structural findings into decisions, a program doc and `/prd` sessions, and closes with the contract §11 trigger chain. It is human-attended throughout; never run it under AFK autonomy. `/review-all --yes` (SKILL.md §Parse invocation) changes one thing here: an item whose analysis converges on a recommendation is ruled by the lead without waiting, and the ruling says so. It does not remove the human from an item that does not converge, from an "accept as standing" disposition, or from committing the trigger-chain gate.

## What goes to the human

Everything structural (contract §6) is deliberated; mechanical findings were already filed by the run. Order the agenda by the synthesis matrix, then take contested items first:

1. a stream with `open_choices`;
2. a contradiction the synthesis could not resolve;
3. an invariant candidate;
4. a `weakened` finding the matrix still ranks in a cell's top three;
5. a critic join error the lead overruled, and any `critic_disputes_severity` the digest flagged;
6. any stream sized `L` or risk `high`;
7. any stream whose `deletable` is empty (a remedy that adds without removing is a cost increase until shown otherwise).

Uncontested streams (one option, confirmed findings, size S/M, low risk) are presented as a block for a single yes/no.

**The sitting shape that worked** (first dark-factory run, 26 streams in one sitting): the high-risk streams one screen each (seven here), then the remaining contested streams in clusters of three or four per screen with one `AskUserQuestion` of up to four questions per cluster, then the uncontested block as one yes/no, then invariant candidates and the weakened list as two more screens. Plan the sitting that way rather than one screen per stream throughout.

## How an item is put

One screen per item, the same shape every time, so decisions are comparable:

- **Finding(s)**: key, anchor, statement, the measurements with their rules, verdict (weakened notes inline), and any severity correction the critic argued for (`change_note` if applied, `critic_disputes_severity` if not).
- **Next change**: the scenario the seat wrote — what an agent does here next and what it costs today.
- **Options**: two to four, each with trade-off (what it costs to build, what it risks breaking) and **long-term consequence** (what the next agent change costs a year on under this option; what becomes deletable; which invariant it would enforce or weaken). Include "accept as standing" as an option when the cost is real but contained — it files an `accepted:<task>` disposition with a reason, never silence.
- **Recommendation**: only when the analysis converges; otherwise say it does not and why.
- **Invariant candidate** (when present): the checkable form and fixture sketch; the existing INV it extends, if any. Promotion is in checkable form only, via the four-site lockstep edit `CONTRIBUTING.md` §6 describes (quality doc §Relationship to the design invariants).

Use `AskUserQuestion` for a choice independent of context; otherwise raise it inline. Push back on an unstated assumption in the framing. Do not relitigate a ruling recorded in a previous program doc unless the finding's evidence changed — cite the ruling.

Under `--yes`, the item is still put in this shape, in the transcript, with its recommendation; the lead then records the recommended option as the ruling and moves on. An item with no recommendation, an "accept as standing" option the lead would pick, or an invariant promotion stops for the human exactly as without the flag.

## Recording

Each ruling is recorded immediately, before the next item:

- in the program doc §Resolved decisions: the ruling, the options considered, the consequence that decided it, the keys it covers, and `ruled_by: human` or `ruled_by: lead (--yes)`;
- as one `decisions_and_rationale` memory with `entities=` naming the tasks or program once they exist (`project_id`, `agent_id` per the overlay), carrying the same `ruled_by` in its text; the program doc is the home, the memory is the pointer;
- an "accept as standing" ruling files a task carrying `x_finding_key`, `x_finding_run`, `source="review-all"` and then cancels it with `metadata.x_acceptance_reason = "<the ruling>"` (contract §7–§8); a `deferred` task is postponed work, never an acceptance, and a `cancelled` task without the reason reads as abandoned. The next run's step 1b keys on that field. `--yes` never makes this ruling.
- a reversed or reworded ruling is a NEW ruling carrying `supersedes: <the earlier ruling>`, never an edit of the old one (solar_challenge_platform R15 was reworded in place; reify S22 R1's reversal lived only in a to-do file);
- a ruling the human makes inside a spawned session comes back in its return's `rulings_in_session` (§Launching) and is recorded here like any other, `ruled_by: human`.

## The program doc

Written once the agenda is exhausted, at the path `report-format.md` §Artefact 3 names, with every section it lists. Streams are sized for one `/prd` session each: a design-heavy stream becomes `spawn`, a stream whose remedy is settled and whose tasks are mechanical becomes `agent`. Each stream lists its finding keys; the G4 table gives every shared artefact one owner before any PRD is authored. G4 is seeded from outside the program too: before authoring, and again at each wave boundary, scan non-terminal PRDs' Files lists and tasks' `metadata.files` outside the program for each stream's touched paths and add their owners as G4 rows (measured on reify: the `codim` clash with pre-existing #6669 surfaced only after S9 had filed). The doc is committed with its wave (§Commit cadence).

## Launching `/prd` per stream

The lead sequences authoring and decomposition; seats and spawned sessions never commit (§Commit cadence) and never edit a shared document. This is what the first dark-factory run found it needed: seats depended on each other's filed task ids for seam dependencies, and six concurrent `git commit` calls in the machine-operated checkout would have contended on the index lock.

- **The seat brief** (either mode) names the program doc, the stream row, the finding keys and the freshness clause, carries the report's `## Mechanical filings` rows for the stream's keys **verbatim** (never the lead's summary of them — the lead's briefs twice asserted a Phase-5 task that did not exist), and instructs the seat to re-run contract §8 step 1 immediately before filing regardless of what the table says.
- **Seat returns** (author and decompose, both modes): ONE structured JSON block, schema `review-all-prd-return/1` — top-level `open_questions` (each with `needs_human`), `rulings_in_session`, `xrefs`, `lead_actions`, and on the decompose pass also `filed`, `held`, `released`, `moves` (`op` ∈ `cancel` | `edge` | `note` | `stamp` | `repath` | `release` | `amend`); field shapes and the `moves` list (paths and symbols the stream moves, renames or deletes, consumed by the delivered-check scan below) per `plans/review-all-program-tooling-prd.md` §Return block (committed with this amendment) — written to the program's state home at `~/.claude/review-all/<run_id>/inbox/<S>.<pass>.json` (the one channel; a spawned session's `result.md` names that path and carries no second copy). The lead applies it, by hand until the program-tooling PRD lands.
- **`agent` streams**: one `/team` run, one seat per stream, `opus`/`high`, in two lead-sequenced passes, author and decompose, with the critic between them:
  1. **Author.** Each seat runs `/prd` author against the program doc with the overlay's conventions and writes its PRD, capability manifest and sidecar to disk; it returns its block and does not commit. The lead reads the open questions and rules on them; the PRDs go into the wave's one commit (§Commit cadence).
  2. **Critic and fold** (both modes; between the author pass and the wave commit). An adversarial critic — `opus`/`xhigh`, or `fable`/`high` for a stream sized `L` or risk `high` — is handed the PRD, manifest and sidecar and the lead's rulings on the stream's open questions (for a spawn stream, with the return's `rulings_in_session`), and attacks premises, buildability, invariant enforcement, semantics, seams and manifest polarity → fold (the critique applied on disk, by the author seat while it is live, else a fresh `opus`/`high` seat) → fold-verifier (`opus`/`high`) → second fold. The fold-verifier is mandatory for size `L` or risk `high`; for other streams a lead spot-check may replace it; a purely prose or check-re-anchoring stream needs neither. Measured on reify: every critic that counted found ≥ 1 blocker (self-reported); two refuted lead rulings made without a code check (S4 OQ-1: the seal created a module cycle; OQ-3: a donor a single-spelling grep missed); fold-verifiers found new majors on every stream that counted (S1 2 blockers, S12 9 majors). Price these seats at the cost gate (SKILL.md §Cost gate) under one stated token-counting rule — reify's 0.3–0.7M per critic and 0.25–0.6M per fold-verifier were under an unstated one.
  3. **Decompose.** The lead orders the streams by the seam graph — a stream that others depend on first (here S14 → S18/S21 → S25 → S23) — and hands each seat, in that order, the filed ids it depends on plus the lead's rulings on its open questions. The seat decomposes under `planning_mode`, adds its `high`/`critical` leaves as dependencies of the trigger-chain gate, runs `commit_planning` on its own batch, writes the stamped sidecar to disk, and returns its block without committing. A leaf that waits on a later stream is a **held leaf** (`report-format.md` §Artefact 3 defines `x_seam_wait`, `release_owner` and `x_seam_released`): filed, wired, excluded from `commit_planning`. Its release owner — the owning stream, or the lead when `release_owner` says so — releases it in four writes, plus a fifth on a re-stamped hold: (1) `add_dependency` onto the delivered leaf; (2) the description rewritten to the contract as delivered; (3) `x_seam_released` stamped; (4) `commit_planning` on that leaf, which runs the delivered-check polarity gate and, once that passes, stamps the sidecar whether or not it flips the row; (5) only if (4) returns `not_planning_hold` (the leaf carries the `until_condition` hold from `report-format.md` §Artefact 3), `set_task_status(status="pending")` on that leaf. `set_task_status` never comes first: it runs no polarity gate, and the leaf is schedulable the moment it is `pending`. Recipe: `plans/review-all-program-tooling-prd.md` §H4 `release`.
  4. **Delivered checks.** (a) Each decompose return lists the paths and symbols the stream moves, renames or deletes; the lead's clerk pass scans every non-terminal task's `metadata.delivered_checks` for those paths and emits the corrections in the same batch, each as three writes: the capability-manifest yaml, its md twin, and the task's `metadata.delivered_checks` as the COMPLETE list. (b) Check patterns are single-line and symbol-anchored; a multi-word phrase that can wrap across comment lines is rejected (reify S23: 9 such checks, 6 vacuous at authoring). The polarity gate's two-sided measurement — fail at the authoring tree, pass after the producer lands (`shared/src/shared/delivered_check_polarity.py`) — is unchanged. (c) Each check is named substrate (verdict `PASS`, green by design) or producer, so the right polarity rule applies. Measured: reify ran six correction rounds over ≈ 50 checks on ≈ 40 tasks in ≥ 10 PRDs; solar_challenge_platform met three hazard shapes (over-broad `absent`, sibling-green, moved spelling).
  5. The lead verifies each filed batch with `get_task` (not `search_tasks`), applies the returned blocks and cross-reference lines to the program doc, and puts the stamped sidecars and the FILED rows into the wave's one commit (§Commit cadence).
- **`spawn` streams**: one interactive session per stream via `skills/spawn/SKILL.md`, with a brief file under the overlay's brief directory in the shape above. The hotspot program (`plans/bug-hotspot-remediation-program-2026-07-06.md`) is the proven shape. A spawned session runs the author pass and returns its block to the lead rather than editing the program doc; its critic and fold (step 2) and its decompose then run as `agent` seats once the rulings exist. The brief tells the session to checkpoint `result.md` after each pass — a checkpoint carries `outcome: in-progress`, only the final write a terminal outcome (the vocabulary is `skills/spawn/SKILL.md` §Result-handback's; `in-progress` is this program's convention until the program-tooling PRD adds it there) — to write `HANDOFF.md` on a context or usage limit, to run `/reflect` before ending, and to END after pass 1. The lead watches `result.md`, not the process: an interactive spawned session waits by design (measured: both Phase 2 sibling sessions of two runs idled ~5 h after finishing).
- Every `/prd` session stamps `metadata.x_finding_key` (list) and `metadata.x_finding_run = <run_id>` on each task it files and runs the contract §8 dedup before filing; the FILED section is written by the lead from the rows the sessions return.

## Commit cadence

All docs changes of a wave — PRDs, manifests, sidecars, the program doc, the state snapshot — go through the lead (or its clerk) and are committed ONCE per wave, in one `git commit --only <paths>`. Seats and spawned sessions never commit; reify's sessions committing their own PRDs is retired. Every docs-direct commit advances main and tends to force the in-flight merge's re-verify; queues are usually busy, and around the dark-factory and reify runs nothing merged for ~10 h; more than `MAX_CAS_RETRIES` (5) direct commits in one merge flight blocks that merge (dark-factory `CLAUDE.md` §Working in the main checkout). The rule holds until the docs-only merge gate (dark-factory task 5411; a 30-day shadow is ruled) lands; after that, program docs go through the merge queue as each PRD is ready.

## Closing: the trigger chain

The contract §11 chain is the program's last act, filed exactly as `skills/_shared/filing-the-trigger-chain.md` §§0–5 says, with `skill = "review-all"` (the bare skill name, per its §0) and this run's `run_id`; nothing about its shape is restated here. What is specific to this skill:

- **Timing.** The gate is filed (§4 interim, or §3 final when the §2 probe in the dark-factory checkout passes) when the first `/prd` stream files; every later `/prd` session adds its own `high`/`critical` tasks as dependencies as it files; `commit_planning` happens only once the program doc's FILED table is complete. `--yes` never runs that `commit_planning`: the human does.
- **Supersede first.** An older open `review-all` chain (§1) is superseded per §5 before this run's gate is filed. When this run was launched from that chain's `review_due` escalation — the normal path once `plans/completion-driven-triggers-prd.md` lands, its id having arrived as `--launched-from` (SKILL.md Phase 0 step 5) — §5 step 2 is where it is resolved, with `ran as <run_id>`.
- **No tasks filed** (program filed nothing): no chain, and the report's `## Method` `extra` says so (§0).

Record the gate id(s) in the program doc's FILED section, then write the run's `observations_and_summaries` memory with `entities=` naming the gate task(s). If the store is unreachable, file nothing and say so in the program doc; the next session files the chain.
