# Memory recall that draws task facts from the task store: findings and proposed design

For Leo, 2026-11-13. Nothing has been changed anywhere. Measurements are from 2026-11-13, read-only, on the
dark_factory project unless stated. Scripts and raw outputs are in `/tmp/team-fused-recall-1113/` (volatile).
This version has been through a critic, who checked the numbers against the scripts and the claims against the
code; the corrections are folded in.

## 1. What we found

### 1.1 How big the problem is

- **Stale status in briefings is uncommon.** Of 120 recent dispatches, 3 (2.5%) were shown a present-tense
  status claim that the task store contradicts: two notes saying "pending" about a task that is done. This is a
  lower bound from one seven-hour window, and the rule only catches "task N is/remains <status>".
- **In the knowledge graph,** 31 of 2,202 finished or cancelled tasks (1.4%) have at least one line that still
  presents the task as open. Also a lower bound.
- **The stale material that matters is knowledge that leans on a task's status:** "X is blocked on task N",
  "this limitation holds until task N lands". In a hand-read sample of 75 status-like items, 13 were of this
  kind, and 5 of the 13 were no longer true. By contrast, of 9 plain "task N is <status>" claims, 8 were still
  true. How often briefings show the leaning kind was not measured.
- So the case for this work is not that agents are often misled today. It is: the principle (one point of
  truth); the "leans on a task that has since changed" class, which nothing handles today; and the chance to
  retire the sentence-parsing clean-up machinery that exists only because status leaks into memory.

### 1.2 Who writes task status into memory

Memory writes since 2026-10-08, all projects: 47,304.

| Writer | What it writes | Writes |
|---|---|---|
| Orchestrator decision notes (not counted on 11-12) | Decisions from a task's plan, into the knowledge graph | 22,234 |
| Reconciliation's completion echo (not counted on 11-12) | "Task '<title>' completed. Landed in commit …" | 4,713 |
| Orchestrator completion note | "Completed: <title>" plus what the task did | 3,822 |
| Reconciliation's task-count snapshot | "40 pending / 12 blocked …" | 1,285 (none for dark_factory, where it is off) |
| Reconciliation's stale-status sweep | "As of <date>, task N has status S." | 33 |
| Agents and interactive sessions, free prose | Anything | about 14,000 |

Sentences that plainly state a task's status are 117 of the 47,304 (0.25%). After reconciliation's sweep stops
(already decided), about 84 remain in 36 days, a little over two a day: decision notes 27, interactive sessions
23, task agents 11, reconciliation's language-model stages 9, others 14.

What shapes the write-side options:

1. **Rules about wording cannot be complete.** Five checks exist today that refuse certain status wordings.
   Four apply only to reconciliation's writers. They catch some forms ("status=blocked", "is currently
   in-progress") and miss others ("Task 1155 remains in-progress" passes all of them). Code that writes from
   inside the server goes around them.
2. **A rule about structure can be complete for the writers that are code.** Every "add" write, from a tool
   call or from inside the server, passes one function in the memory service.
3. **The knowledge graph rewrites what is written.** Its library's own language model turns text into facts,
   and we do not control that step. A task's summary in the graph is simply its facts joined together.
   It does keep dates: 224 of 235 status facts carry the date they were true, as a field.
4. **Code cannot reliably tell a current claim from history by wording.** A rule built on tense and dates,
   tested on the 75 hand-labelled items, was right 6 times out of the 11 it called "current claim".

Completion notes and the completion echo are history: all 25 sampled were still true. Both already carry the
task's number as a structured field.

### 1.3 What a recalled memory carries today

- A search result is text plus the date it was true. Its field for "what this is about" is always empty.
- A pipeline for "which tasks is this write about" already exists on the knowledge-graph side: it takes the
  writer's declaration first, then the writer's task field, then a scan of the text, and records which it
  used. Since 2026-10-08 writers declared a task on 5.3% of graph writes. On the notes side (the other store)
  a declaration is checked for typos and then thrown away.
- **The text scan that recognises task mentions makes mistakes that matter here.** I ran it:
  "Reify task 3674 was cancelled" is read as dark_factory's task 3674; "task 8c7e163fcf" (a commit) as task 8;
  "tasks 2226 and 2227" finds only the first; a usage example mentioning "Task 3127" counts as a real mention.
  Two of the 75 hand-read items were such cases. If we print live status for every scanned mention, some of
  it will be another task's status.
- A dispatch's briefing mentions a median of 7 distinct tasks (90th percentile 14). 88% are done.
- In the graph, relation names such as BLOCKS or FIXES are chosen by the library's language model. Several
  read by hand had the wrong direction or meaning.
- Defect found on the way: a briefing's block about its own task is meant to show the newest ten facts with
  dates, but the reply it reads has no dates, so the ordering and dates do nothing.

### 1.4 What the task store can answer, and what it costs

| Fact | Available for |
|---|---|
| Status, priority, title | every task |
| What it waits on, and whether those are finished | every task |
| How it finished (merged, already on main, a gate, …) and the commit | 86% and 81% of done tasks |
| Declared files | 76% of tasks |
| Date created | 1% (recorded only since 2026-11-12) |
| History of status changes | not in the task store; the 20 GB write journal has it since May, without reasons |
| Escalations, merge-queue state | outside the task store, owned by other packages |

Reading the status of 20 tasks takes 0.1 to 0.4 milliseconds. Searches run about 2,600 a day across all
projects, lookups of a named thing about 870. Status reads on all of them would add 3 to 4% to what the server
already serves. Reading the further facts (waits-on, how finished) for a batch of tasks has no existing
function and was not timed; it is the same small database.

Other projects: the server reads all 12 registered projects' task stores from one process, and already
distinguishes "no such task" from "could not check".

### 1.5 Other ways to recall tasks

- **By content:** the task search exists (every task's title, description and files, by meaning, with live
  status). Its use is not logged, so we do not know how much agents use it.
- **By file:** no way today from a file to the tasks that touched it. The data exists.
- **By subsystem:** no field. Can be derived from declared files; about two thirds of tasks fall in one area.

### 1.6 Neighbouring work

Pending tasks declared on the files this would touch: the server's main file 135 (and one in progress); the
task-store middleware 63; the memory service 54; the orchestrator's workflow file 246; the briefing renderer 5.
Tasks on the same file run one after another.

- The review-all plan that splits the server's main file (draft, no tasks filed) has a step that moves `search`
  out and turns the nested status-read helper into its own module. That step is weeks away.
- Task 3139 (pending since July; a leaf of the committed memory write-path plan) lets a writer put "re-examine
  this when task N finishes / when file F changes" on a memory. Its motivating case is "this limitation holds
  until the fix lands". Task 3140 (waits on 3139) acts on it: when a task finishes, it flags memories carrying
  that field, or whose text matches a "blocked on task N" pattern, for a second look.
- The reconciliation sweeps plan keeps the status-sentence detector as a backstop until this session sets a
  rule, and keeps the task-count snapshot (moving its code). It hands the snapshot question to this session.

## 2. Proposed design, as decisions

### Decision 1. Show live task facts with recalled memory

**The choice:** where live facts are joined in, and whether stored status wording is hidden.

- **A (recommended). The memory server adds live facts to its replies; briefings show them; nothing is hidden.**
  Replies from search and from the lookup of a named thing gain a small table of the tasks involved, with live
  facts (Decision 2). The briefing prints it as one block, grouped by status, with a line saying that status
  words inside memory text are history and the block is current. Agents' own searches get the same table, and
  so do reconciliation's language-model stages. Code that reads memory to compare or de-duplicate it keeps
  getting the raw text. If the task store cannot be read, the block says so.
- **B. Briefings only.** Agents' own searches, interactive sessions and reconciliation still see text alone.
- **C. A, and also hide status sentences.** Needs the wording classifier that is right about half the time.

### Decision 1b. Which mentions count, including other projects' tasks

**The choice:** how a memory is tied to a task before live facts are printed for it.

- **A (recommended). Structure first, text second, and say which.** A task is "about" a memory when a
  structured link says so: the graph thing named for the task, the task field on completion notes, a writer's
  declaration. Those are printed as firm. Tasks found only by scanning the text are printed as "mentioned",
  always with the task's title beside the number, so a wrong match is visible to the reader. The scan is fixed
  for the cases found ("Reify task N", commit hashes, lists). A task of another registered project is looked up
  in that project's store; an unregistered project prints "could not check".
- **B. Structured links only.** Never wrong, but covers a minority of memories today (5% declared on graph
  writes; none stored on notes).
- **C. Every scanned mention, printed as fact.** Simplest; will sometimes print another task's status as
  current.

### Decision 2. What counts as a task fact, and where history lives

**The choice:** the line between what memory may hold and what comes from the task store.

- **A (recommended). "Memory holds what happened and what was learned, each with its date. The task store
  answers what is true now."** Attached per task: status; title; for an unfinished task, the unfinished tasks
  it waits on; for a finished one, how it finished and the commit. Every fact shown from memory carries its
  date (already true for search results; the briefing's own-task block gets fixed). Completion notes stay.
  History of status changes stays in memory; we do not rebuild it from the journal.
- **B. Status and title only.** Smaller first step; "waiting on what?" is left to a second call.
- **C. Everything, including escalations and merge-queue state.** Those live in other packages; larger, later.

### Decision 3. The write side

The principle stands: nothing writes task status into memory. **The choice** is the mechanism.

- **A (recommended). A structural rule for code, an immediate correction for agents, and no wording rules.**
  1. *Code that writes memory* passes the task as a structured link and never puts a status value into the
     text. A test enforces it. This covers the completion echo, the completion note, the decision notes and
     the small writers inside the server.
  2. *Every write that names a task gets the live facts for it back in the reply*, from the same function
     recall uses. An agent that writes "task N is pending" is told on the spot that N is done. No classifier.
  3. *The five wording checks are retired* along with the detector (Decision 6), once reconciliation's own
     writers have stopped.
  4. *Guidance* for agents says: do not record a task's status; record what happened, with its date; declare
     the task.
  Consequence: roughly two status sentences a day will still be written by agents. Every reader sees live
  facts beside them.
- **B. A, plus a language-model check on writes.** The existing write-triage judge is given the live facts and
  tags (never refuses) a write that asserts current status. Consequence: a model call on writes for about two
  cases a day.
- **C. Refuse status wording from every writer.** Wrong about half the time; code inside the server goes
  around it. Not recommended.

Against your partition principle, A gives: code does the structural rule and the echo; no language-model
judgement in this area; the human hatch is the flag in Decision 4.

### Decision 3b. The task-count snapshot

**The choice:** reconciliation writes "40 pending / 12 blocked" into memory each cycle for projects where it is
on (off for dark_factory and three others).

- **A (recommended). Retire it for every project.** It is a copy of status. Anyone needing counts reads the
  task store. Its parser and the filters that exist to handle it go too.
- **B. Leave it as the sweeps plan has it** (code moved, per-project switch kept).

### Decision 4. Relations between a task and a thing

**The choice:** what is stored and what is computed.

- **A (recommended). Store the writer's declared link and relation word; compute everything about status at
  recall; keep one flag for a human.**
  - *Stored:* extend the existing "which tasks is this about" pipeline to the notes store, so a declaration is
    kept on every memory. Add an optional relation word from a short list: **blocker**, **cause**, **fix**,
    **relevant**. No status is stored.
  - *Computed at recall:* a mention with no declared relation is "relevant". A declared relation is evaluated
    against live facts, telling done from cancelled: a blocker whose task is done shows "blocker cleared
    (commit X)"; cancelled shows "blocker withdrawn"; a fix whose task is pending shows "fix not landed";
    cancelled shows "fix abandoned". This is your "predicate status of task is relation to thing" with a fixed
    predicate per relation word. Free predicates can follow.
  - *First step ties a task to a memory.* Tying a task to a thing in the knowledge graph (where one write
    becomes several facts) is designed in the second plan.
  - *Tasks 3139 and 3140:* 3139 becomes "keep the declared task and relation on the memory" (its file-changed
    half is unchanged). 3140 keeps its job as the flag for a second look when a task finishes, on declared
    relations only; its text pattern is dropped.
- **B. Have a language model label relations on existing memories.** The graph library already does this, and
  its labels were unreliable.
- **C. Keep 3139 and 3140 as filed.** A second mechanism beside recall, one half of it parsing text.

Limit: declared relations exist only where writers declare them (5% today). Everything else gets Decision 1.

### Decision 5. Other recall routes

**The choice:** which to build, in what order.

- **A (recommended).** (1) Log use of the task search, and add "most similar other tasks, with live status" to
  briefings. Small. (2) Build file-to-tasks from declared files and finishing commits, and show "tasks that
  recently changed the files you are about to change" with the notes those tasks left. Most new value; needs
  a new index. (3) Subsystem, derived from files, only if (2) shows a need.
- **B. None now;** revisit after Decisions 1 to 4 are in use.
- **C. Mix task search into every memory search.** Two rankings in one list; a second search on every call.

### Decision 6. Existing stale and historical material

**The choice:** leave, annotate at read time, or sweep.

- **A (recommended). Leave it, annotate at read time, then retire the status-sentence detector, its sweep and
  the five wording checks.** The test for retiring: live facts are shown on search, on lookups, in briefings
  and to reconciliation's own stages. Consequence to accept: stale status facts stay in the graph and still
  rank in search; readers see them next to live facts.
- **B. Annotate and keep the detector running.** Keeps the parser and its follow-up tasks for a problem of
  about 1%.
- **C. One-off clean-up of old status sentences.** Needs the same unreliable classifier.

### Decision 7. Shape of the work

**The choice:** one plan or several, and whether to wait for the server split.

- **A (recommended). Two plans; the first now.**
  - *Plan 1: live task facts at recall and at write.* Decisions 1, 1b, 2, 3, 3b, 6. About 9 to 11 tasks.
    First task: turn the nested status read into its own module and add the batched read of the further facts.
    That is the step the server-split plan intends; we ask that plan's lead to let it land early under the
    name they chose. Then, in order: the reply tables; the briefing block and its date fix; the scan fixes;
    the write reply; the code-writer rule; retirement of snapshot, detector, sweep and wording checks last.
  - *Plan 2, after plan 1 is in use:* Decisions 4 and 5.
- **B. One plan.** Relations and routes get designed before the first part has been seen working.
- **C. Wait for the server split.** Weeks; none of its tasks exist yet.

Changes for the review-all program's lead, to be written to their rulings file once you rule: the detector's
end condition (Decision 6); the snapshot (3b); the sweep task shrinking to "stop writing"; the status-read
module landing early (7).
