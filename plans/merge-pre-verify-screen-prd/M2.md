## 1. How the event store records a main-health red verdict

- **Event:** `events.event_type='merge_attempt'`, payload `{"outcome": "main_health_red"}`; since task 2565 also `"origin_host"` and `"probe_host"` (97 of the 109 in the window carry them = deferred probe path; the other 12 are the synchronous path). `task_id` = the item whose verify failed and triggered the probe. Emitter: `merge_lane/gates.py::_emit_merge_attempt` with `OutcomeKind.main_health_red`, called from `merge_lane/worker.py::_classify_main_health_red` (sync) and `::_run_deferred_main_health_probe` (deferred).
- **No sha, no train id, no failing tests on the row.** It is keyed on nothing. The probe sha (`verify_failure_is_preexisting_on_main` returns `(True, main_sha)`, the bare-main HEAD the probe tested) is used only inside the escalation dedupe fingerprint (`workflow.py::compute_preexisting_main_break_fingerprint`), a hash that cannot be reversed. `merge_attempt.duration_ms` is empty for this outcome.
- **Companion rows:** in deferred mode the item's own `merge_finalized` (state blocked) and `merge_blocked` rows carry the PROVISIONAL task-fault reason (disposition `branch_bug`) with the `FAILED <test>` lines; the main-health reason (`Main-health red: ...`) appears on `merge_blocked`/`train_derailed` for only 12 of 109 verdicts (the sync path and trains).
- **Rule: red base sha R** = the main HEAD at the verdict timestamp, from `git reflog show main` (2,466 entries, 2026-07-28 onwards, `%H` + timestamp; main_at(t) = last entry at or before t). One override: verdict 314159 (task 3473, 2026-08-07T08:48:44Z) was emitted 21 s after main advanced to the fix commit, so it is attributed to the pre-fix sha 69340530. Deferred verdicts are protected by the probe's own staleness check (probe_sha must equal current main), so R equals the probe sha for them; for the 12 sync verdicts it is an inference.
- **Rule: failing tests of a verdict** = the `FAILED <id>` / `not present on main: <ids>` lines of the triggering verify's block text (the same task's failed merge_verify, nearest `merge_finalized`/`merge_blocked`/`train_derailed` within -10..+400 s of its end); 108 of 109 have a set (the other, task 6160, has none).
- **What the lane does after a verdict (code):** `worker.py::_auto_heal_main_health_deferred` halts the 'normal' lane only for `AUTO_HEAL_MECHANICAL_CATEGORIES = {'compile_error'}`. Every verdict here is `test_failure`, so branch (d) applies: escalation plus (since task 5471, landed 2026-10-21) an owned fix-main task (`main_health_fix_owner.py`, `metadata.main_health_signature`, `spawn_context = main_health_fix_filed`), and NO lane halt. That is why verifies keep starting. After 5471 only one episode exists (10-24, task 7449); its members were re-pended behind 7449 (`age_anchor_reset`, anchor 7449, 09:41:38Z).

## 2. Verifies started on a judged-red base

**Rule (population):** every `merge_verify` row (2,517 since 2026-07-30; start = row timestamp minus `duration_ms`, which matches the E3 train to within 1 s) whose start lies in [first verdict on R, the first main advance after that verdict) and whose merge commit's first parent has R as an ancestor (`git merge-base --is-ancestor`). 102 of 102 candidates inherit R (`main_at(start) == R` for all). Excluded: verifies that started before the first verdict (see 2d), task-side `workflow_verify` (a different, pre-merge gate), verifies cancelled mid-flight (no row, so counts are a lower bound), and verifies on a stale base that does not contain R.
**Rule (kind):** `speculative=True` and `chain_items>1` = chain tip; `speculative=True` otherwise = speculative (depth>0 = stacked link); a `train_started` row for the same tip task within 10 min of the start = coalesce train; `speculative=False, depth=0` = solo. Declared atomic trains emit no `train_started` row and cannot be told apart here.
**Rule ("same tests"):** `same` = every failing id of the verify is in the red sha's verdict failing set; `overlap` = some; `different` = none; `n/a` = no failure text found (all 8 are coalesce trains in A). Test ids are matched module-qualified.
**Rule ("item is fix"):** task title matches RED MAIN / Fix-forward / Re-green / fix main / MAIN RED, or `metadata.main_health_signature`, or `spawn_context` in steward-main-red / main_health_fix_filed. No single machine marker exists before 5471: fix items carry `merge_lane: high` (5088, 4471, 7449), `spawn_context: steward-triage` (6567, 7124) or `steward-main-red` (5230). Of all fix items touched here, only 7449 carries `main_health_signature`.

## 4. Red-episode lifetimes

**Rule (sha level):** time from the first verdict on R until main advanced past R (next reflog entry). n=36: median 107 min, p25 32, p75 226, max 380. A: median 107 (n=31); B: median 18 (n=5; p75 159, max 284). Time from main reaching R to the first verdict (detection lag): median 68 min (p25 57, p75 116, max 216; B median 80).
**Rule (episode level):** consecutive red shas chain into one episode when their failing-test sets overlap (or one is empty), no landed merge (`merge_finalized` state done, or `train_merged`) falls between their first verdicts, the earlier sha's advance was not a fix, and the gap is under 8 h. This yields 23 episodes (A 18, B 5). First verdict to the last red sha's next advance: median 147 min, p25 18, p75 284, max 1,360 (09-03 deploy-pause episode, 16 verdicts). First verdict to the first landed merge afterwards (proxy for "the lane next saw green", since a landing needs a passing full-tree verify): median 283 min, p25 40, p75 1,003, max 1,499.
**Implication for S1.2:** 25 of the 36 red shas were ended by an advance that did not fix the break: 20 direct commits (15 docs, 4 nightly census/legibility, 1 other) and 5 unrelated tasks whose full-tree verify passed on the red base (5b). 11 were ended by a fix: 6 direct fix commits and 5 fix tasks (4471, 5088, 5230, 6567, 7124). A "judged red" flag keyed on the red sha therefore expires at the first harmless commit while the break persists (13 of the 36 red shas are re-sightings of an earlier sha's break within an episode); keyed on the failing signature it has to hold until a landing proves green, a median 283 min and up to ~25 h (max 1,499 min) after the first verdict.

## 5. Could a verify on a judged-red base pass?

### 5a. The "not present on main" comparison never makes a pass

Code read (`verify.py::verify_failure_is_preexisting_on_main`, `::diff_new_failures`, `::partition_new_failing_ids`, `worker.py::_run_post_merge_verify` around the `new_ids` block): the id-diff against main's per-sha failing baseline runs only AFTER a merge verify has failed. Its outputs are (a) wholly preexisting, so a `MAIN_RED` blocked outcome and `main_health_red`; (b) attributable new ids, so a task-fault blocked outcome whose reason says `N new failing test(s) not present on main`; (c) all-new-ids-skipped-on-main, fall through to the signature probe. None of them returns `passed=True`. The other baseline reader is the trivial-pass gate (`worker.py` around `known_failing_ids_on_main`), which WITHHOLDS a config-only pass over a known-red main. So a verify on a known-red base cannot pass by subtracting known failures; a whole-tree verify passes only if the red tests are fixed in its tree, or green in that run.
The one other route to a pass with a red unit is flake suppression: 2 of 270 `merge_verify` rows with unit outcomes since 10-13 are `passed=true` with one `ran_red` unit (task 6125, 2026-10-29T12:14Z, speculative depth 1; `merge_flake_suppressed` isolated re-run). None of those is on a judged-red base.

## 6. Caveats and what I could not verify

- `merge_verify` rows exist only for verifies that finished; cancelled or drained ones are missing, so counts and minutes are a lower bound.
- `duration_ms` can include remote waiting; host-minutes = wall minutes of the verify, not CPU.
- R attribution uses the reflog (main_at(verdict ts)). The reflog starts 2026-07-28, which covers the window. Deferred verdicts are guarded by the probe's staleness check; the 12 sync verdicts are unguarded and a skew of a few minutes could move a start across a main advance.
- 8 coalesce-train starts in A have no failure text found, so "same tests" is unknown for them (all counted as failed waste; ~450 min).
- Chain-era evidence is absent: C has 0 verdicts in 1.8 days, 2 chain verifies in the whole data set. Nothing here measures chain behaviour on a red base.
- The memo's claim "None involved an MCP member" and the 56-train figure were not re-derived (out of scope).
- Declared atomic trains cannot be separated from solo/reverify rows in `merge_verify` (no `train_started` row for them); `depth=null` rows (47 in the window) were classed as coalesce train only when a `train_started` matched.
- Fix-item detection is heuristic before task 5471 (only 7449 carries `main_health_signature`); title and lane markers were used. `fable-evidence-isolation` has a non-numeric id and no task-store title.
- No write tool was called; scratch only under /tmp/stream1-M2/.
