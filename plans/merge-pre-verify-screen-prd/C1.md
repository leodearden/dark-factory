## 0. The lane in one picture

```
workflow submit ─┐                                     MCP merge_request ─┐
 (register_and_enqueue_merge_request)                   (coalesce_or_enqueue_merge_request)
                 └──────────► asyncio _queue ◄──────────┘
                                │  _acquire_next_request (13959): _drain_queue_into_lanes → recompute_suffix_conflict_graph
                                │     → _bounce_conflicting_suffix_items [needs_rebase bounce] → _pop_next_pickable
                                ▼
 _merger_loop (16523, ONE serial task)   _lane_buffers hold the unfrozen suffix = chain-link candidates
   GroupMergeRequest? ──► _do_train_merge (inline, own verify)  [paths 4, 5]
   else: classify_and_merge (5891) → git_ops.merge_to_main → fresh `_merge-<hex8>` worktree at the MERGE COMMIT
         → _check_plan_targets_in_tree (drop guard) → RealMergeItem(merge_wt, base_sha, speculative)
         → _verifier_queue.put;  then look-ahead: next pickable req merged onto this merge commit (speculative=True)
                                ▼
 _verifier_loop (17431, ONE serial task): dispatch-fill → _dispatch_item (22290) → allocator.acquire(host)
         → _deep_chain_placement [slot 2 only] → asyncio.ensure_future(_run_inflight_verify)
 _run_inflight_verify (19084): local lease = warm-swap to a lane re-checked-out at merge sha; remote lease = no swap
         → _lane_post_merge_verify → _run_post_merge_verify (2451) → pool.dispatch (LocalRunner | RemoteRunner/laptop)
                                ▼
 _finalize_inflight (21214), in submission order: CAS advance_main → [rebased? gate re-verify] → _finalize_advanced_merge → resolve Future
```

"Slot 1" = a non-speculative item (merged on real main, `base_sha == main`); "slot 2" = `speculative=True` (merged onto the predecessor's merge commit). `SpeculationController` (`merge_lane/speculation_controller.py`) does NOT dispatch anything: it is the permit / look-ahead state machine of the merger side (`take_prefetched`, `base_for`, `on_dequeue` ATTACH/FALLBACK, `acquire_for_lookahead`, `on_lookahead_found`, `on_transfer[_terminal]`, `on_abort`). The verify decision sits in `_dispatch_item`.

## 1. The five dispatch paths

### 1.1 Sequential / slot-1 head verify of a single request
- Dispatch: `worker.py::SpeculativeMergeWorker._merger_loop` → `worker.py::classify_and_merge` → `_verifier_queue` → `_verifier_loop` → `_dispatch_item` → `_run_inflight_verify` → `_lane_post_merge_verify` → `worker.py::_run_post_merge_verify`. The same path is re-entered by `worker.py::SpeculativeMergeWorker._remerge` (calls `classify_and_merge` with `speculative=False`) after head failure cascade, Mechanism-2 stale-main discard, or dead-base discard (`_chain_dead_link`).
- Tree verified: the merge commit "branch tip merged `--no-ff` onto real main" (`base_sha` = main at merge time). Local lease: `_acquire_warm_verify_worktree` (`merge_lane/liveness.py`) re-checks the merge sha out in the persistent `_merge-verify` lane or a `_spec-` warm lane, the ephemeral `_merge-<hex8>` is deregistered. Remote lease (laptop, `verify_host_policy: prefer_remote` in `dark-factory-orchestrator.yaml`): no swap; the laptop verifies the same sha in its gate checkout. In both cases `item.merge_wt` (ephemeral `_merge-*`) exists on the workstation with the merged tree checked out until after dispatch/finalize.
- 1b. Gate re-verify (a second verify dispatch for the same item): after a green verify, `_finalize_inflight` calls `advance_main`; if main moved and the branch had to be rebased, `gates.py::_reverify_rebased_tree` runs `gates.py::_decide_reverify_gate` (no verify) and then `_gate_reverify_on_head_host` → `_lane_post_merge_verify` on the head's own host. Decision reasons (`merge_lane/reverify_gate_decision.py::ReverifyGateReason`): `same_tree` (only if `merge_gate_history_pure`), `same_tree_history_leg` (runs only `merge_gate_history_test_command`), `disjoint`, `disjoint_untrusted`, `overlap`, `overlap_unknown`. In this repo `_disjoint_skip_blockers` always blocks the disjoint skip (`merge_verify_breadth: "full"` is P1). This is an existing pre-verify classifier but it classifies "is a re-verify needed", not "is the tree defective".
- Existing pre-verify checks before the verify starts, in order: `_request_abandoned`; `_classify_branch_presence` (unknown_branch / already_merged); `_unstack_before_merge` (stack on never-landed base); `is_ancestor` + `_already_merged_is_genuine` / `patch_content_contained` (already_merged); `git_ops.merge_to_main` (conflict / merge failure); `_check_plan_targets_in_tree` (dropped plan targets); `prior_timeouts >= MAX_POST_MERGE_VERIFY_TIMEOUTS` (abandoned_verify_timeouts); at dispatch: operator halt / `is_admission_halted`, `_chain_dead_link` (INV-3 dead base), Mechanism-2 `main_advanced` re-merge, `allocator.free_host_count()`; inside `_run_post_merge_verify`: `verifier.ensure_disk_space` (returns `MergeOutcome('blocked', verify_skipped=True)` BEFORE any verify; the closest existing precedent for a screen bounce).

### 1.2 Speculative slot-2 verify (merge-ahead)
- Dispatch: same chain as 1.1; the difference is made in `_merger_loop`: after item N is merged and queued, `SpeculationController.acquire_for_lookahead` + `_pop_next_pickable` find N+1; next iteration `take_prefetched()` returns it, `base_for(actual_main)` returns `spec_base` (N's merge commit), `classify_and_merge(..., speculative=True)` merges onto it. K = speculation depth (2). A late arrival can ATTACH to an in-flight predecessor (`on_dequeue`, task 1862).
- Tree: main + all unlanded predecessors + this item. `RealMergeItem.speculative=True`, `base_sha` = predecessor merge commit. Consequence for any whole-tree screen: a predecessor's defect shows up in this item's tree.
- Extra pre-verify decisions: `_dispatch_item` skips the stale-main re-merge for speculative items; `_probe_verify_placement` (relabel only, off by default); `_deep_chain_placement` (1.3). Delivery quirk: `_oob_deliver` never early-delivers a `Decided` outcome for a speculative item (it can be discarded and re-merged), so a speculative bounce is delivered in submission order at finalize as a passthrough and sets `_n_failed=True` (next speculative dispatch discards its build with reason `previous_failed`).

### 1.3 Deep chain tip
- Build + dispatch: `worker.py::SpeculativeMergeWorker._deep_chain_placement` (13108), called from `_dispatch_item` AFTER `allocator.acquire` and the lease/permit leak guard, only for `item.speculative`. Guards in order: not speculative; `merge_deep.chain_cap <= 0`; `task_id in _chain_error_suppressed`; `chain_snapshot()`; `select_chain_depth(cap, 1+len(snapshot), _chain_halving_state)` (needs queue>=2, target>=2). Then `build_chain` under `asyncio.timeout(CHAIN_BUILD_TIMEOUT_SECS = 120 s)`; timeout / exception / lane unavailable / zero links all degrade silently to the ordinary adjacent verify.
- `worker.py::SpeculativeMergeWorker.chain_snapshot` (12432): READ-ONLY tuple of `_lane_buffers` in pick order (high lane first, FIFO; halted lanes skipped; no clique-minimality). No pop, no transition, no future resolved.
- `worker.py::build_chain` (6206): one scratch lane (`acquire_chain_build_lane` → `acquire_spec_lane`; refuses the serial `_merge-verify` lane), lane HEAD must equal the dispatching item's merge commit (`lane_base_mismatch` otherwise), then per link: `_link_refusal` then `git_ops.merge_branch_into_worktree(lane, req.branch.bare_id)`. `worker.py::_link_refusal` (6450) refuses only `GroupMergeRequest` (`train_request`) and `git_ops.unlanded_stack_base(...) is not None` (`stacked_on_unlanded_base`). Truncation (`ChainTruncationReason`: conflict, train_request, stacked_on_unlanded_base, already_merged, merge_error, lane_base_mismatch) stops the chain at the first bad link; the truncated link is NOT given an outcome (decision 4 in `plans/deep-merge-ahead-prd.md`); the reason is logged only (`build_chain: ... reason=`), no event carries it.
- Tree verified: `chain.tip` = I0's merge commit + each link merged `--no-ff` in order, checked out in `chain.lane` (a `_spec-*` pool lane). `_run_inflight_verify` bypasses the warm swap on this arm; `chain_items = 1 + len(chain.links)`; the lane is released exactly once in the `finally`; I0's own ephemeral worktree is kept until the adopt/non-adopt decision (`_drop_chain_item_ephemeral_wt`).
- Pass: `_adopt_head_on_tip_authority` then `worker.py::_land_chain_prefix` (20885) walks links in order: `_take_chain_link_request` → `_journal_landed_then_advance` (`merge_wt=None`, `max_attempts=1`, `expected_main` chain, `reverify_on_rebase=True`) → `_finalize_advanced_merge` → `_resolve_or_drop_abandoned`. First non-`advanced` result, lease contention or exception stops the walk with the link restored to its exact lane slot and NO outcome rendered; halting results (`_HALT_ADVANCE_RESULTS`) still halt the queue.
- Fail (tip red): `_run_post_merge_verify` returns a `MergeOutcome('blocked', reason=...)`, but `_run_inflight_verify`'s chain arm DISCARDS `out`. It calls `_note_chain_outcome(False, 1+len(links))`, logs "a red tip names no culprit, so every chained item takes its ordinary sequential path", and `_requeue_from_verify(item, entry_slot)`: only I0 is put back on `_queue` (via `_requeue_request`, its Future stays pending); the links never left `_lane_buffers`. `_finalize_inflight` then sees `REQUEUED`, sets `_n_failed=True` and returns False (head-failure cascade for any downstream in-flight entries; next speculative dispatch discards its build as `previous_failed`).
- Halving state: `SpeculativeMergeWorker._chain_halving_state: int | None` (10311), in-memory, per worker process (reset to `None` on restart), global (not per item). Single writer `_note_chain_outcome` (12895) via `worker.py::next_halving_state(passed, depth)`: fail → `max(1, depth // 2)`, pass → `None`. Two call sites, both in `_run_inflight_verify`: the chain arm (once per chain, with BUILT depth) and the d=1 floor reset (a PASSING non-chain slot-2 verify while state is not `None`).
- What counts as a tip fail: ANY non-`None` `MergeOutcome` returned by `_lane_post_merge_verify` on the chain arm, which includes disk-guard skips (`verify_skipped`), ENOSPC / classified infra-transient holds, timeouts, `MAIN_HEALTH_RED` and `TRIVIAL_PASS_MAIN_RED` outcomes, and genuine reds. What does NOT halve: an exception (goes to `_chain_error_suppressed`, requeue, next dispatch of that task verifies un-chained), `RunnerUnavailable`, lease contention, abandon, operator halt, no-progress abort (all return earlier). A tip verify on a red base therefore both wastes the verify and halves depth (relevant to S1.2).
- Thrash guard and why deep failures never feed it. The guard is workflow-side: `workflow.py::TaskWorkflow._check_merge_outcome_thrash` + `workflow.py::_evaluate_merge_thrash`, threshold `config.py::max_consecutive_merge_thrash` (default 2), counter `retry_ledger.consecutive_merge_thrash`. It is fed only from `workflow.py::TaskWorkflow._run_merge_phase`, after `_submit_to_merge_queue` returned `REQUEUED` with `_last_merge_block_reason` set, which happens only in the generic `blocked` fall-through of `_submit_to_merge_queue` (after the human-judgement prefix short-circuits). The signature is `shared/task_metadata.py::RetryLedger.compute_merge_outcome_signature`: sha256[:16] of (`failure_category`, normalised `failure_cause_hint`) when either is set, else of the normalised reason. A chain failure feeds it nothing because no `MergeOutcome` is ever delivered to the waiter: the tip's `out` is dropped, the requeue leaves the Future pending, and `_land_chain_prefix` aborts silently. `build_chain` and `_land_chain_prefix` comments give the rationale: a deterministic reason string repeated every round would trip the ladder into a false human escalation (the 3003 `MergeVerifyLeaseContended` class). The needs_rebase bounce solves the same problem the other way, by embedding an ordinal in its reason (`suffix_graph.py::SuffixConflictTracker._escalate`; pinned by `orchestrator/tests/test_merge_queue_bounce.py::TestBounceEscalationsNeverFeedTheThrashLadder`). Other guards that exist and are separate: `_post_merge_verify_timeouts` loop-breaker (per task id, bumped when `verify.timed_out`), the probe's `_recent_verify_outcomes` window (`_record_verify_outcome`, fed only by non-sentinel finalize, so NOT by a requeued chain tip), `NoLandingsCircuitBreaker` (disk + zero landings).
- How a single link's own defect currently propagates (by reading; no chain tip red has occurred yet): the link is not named anywhere. Tip red → depth halves (6→3→1) → I0 requeued → the defective link stays buffered and eventually becomes a dispatching item at the floor (or a slot-1 head), where its own solo verify fails and returns a real `blocked` outcome with text to its own waiter. Failure text on the way: the chain tip's `MergeOutcome.reason` is dropped; what survives is (a) the verify log under `data/verify-logs/<I0 task id>/attempt-N.<module>.summary-*.json` (keys: category, cause_hint, label, rc, cmd, commands), keyed on the DISPATCHING item, not the culprit; (b) the `merge_verify` event row (`passed`, `chain_items`, `chain_build_ms`, plan hash, per-unit results; no reason text); (c) side effects that `_run_post_merge_verify` runs for I0 as if I0 had failed: `_spawn_merge_verify_dry_run` (a dry-run investigation reading I0's worktree, if `unblock_auto.enabled` and not timed out), `_spawn_main_health_probe` (deferred probe of bare main), merge-skew classification (when base facts supplied, they are), timeout loop-breaker bump on I0. Observed: since the flip there are 2 chain verifies, both passed (rule: runs.db `events`, event_type='merge_verify', `json_extract(data,'$.chain_items') >= 2`, all rows to 2026-10-29T18:31Z, n=2: task 6102 chain_items=3 local, task 6175 chain_items=2 laptop). So the fail path is unexercised in production.

### 1.4 Declared atomic train
- Admission: members carry task-authored `metadata.train` (`plans/orchestrator-atomic-train-merge-prd.md`; or set by the workflow-side former `workflow.py::TaskWorkflow._maybe_form_train`, which Leo ruled OFF). Each member's `_run_merge_phase` starts with `_maybe_defer_as_train_member` → `_enter_merge_deferred` (status `merge-deferred`, member does not enter the queue). The tip member's workflow calls `workflow.py::TaskWorkflow._maybe_enqueue_group_merge` (1795): all members must be `merge-deferred` and self must be the last; it builds a `GroupMergeRequest` (members, `status_check`, `mark_member_done`) and calls `register_and_enqueue_merge_request`. Union scope: `_union_train_scope` unless `merge_verify_workspace`.
- Dispatch: `_merger_loop` sees `isinstance(req, GroupMergeRequest)` → `_await_unadvanced_predecessor`, `is_admission_halted` → `_stand_down_train`, else `worker.py::_do_train_merge` (7276) INLINE in the merger task (no other merge starts meanwhile). Order inside: verify-timeout loop-breaker; `req.status_check` all `merge-deferred` (else `TRAIN_INCOMPLETE`, retryable); `rebase_onto_main(req.worktree)` (conflict → `TRAIN_REBASE_CONFLICT`); `merge_to_main(req.worktree, tip)` → `merge_wt`; `_leased_train_verify` (`_TrainVerifyHost.acquire`: leased host, remote only for trains <= `_TRAIN_REMOTE_VERIFY_MAX_MEMBERS`, local fallback on `RunnerUnavailable`) → `_run_post_merge_verify` with NO handles (so no dry-run, no deferred main-health probe, synchronous `_classify_main_health_red`, no skew classification); `_advance_train` CAS loop with `reverify_on_rebase=True` (same `_reverify_rebased_tree`); `_finalize_advanced_merge`; `mark_member_done` per member only after the land.
- Tree: tip branch (which by stacking carries all members) rebased on main, merged `--no-ff` in a fresh `_merge-*` worktree (`merge_wt`). The merge worktree is local to the workstation as well.
- Failure routing: `worker.py::_derail_on_train_verify_failure` tags a structured red with `TRAIN_VERIFY_FAILED_REASON_PREFIX` (unless main-health-red); `workflow.py::TaskWorkflow._maybe_enqueue_group_merge` then routes the prefix to `_attribute_train_failure` (N solo `reverify_member_solo` verifies, passers land); any other `blocked` → `_mark_blocked(escalate_to_human=True)` (human L1, no steward). A screen failure on a train must pick one of those two: tagged (triggers the N solo verifies) or untagged (human L1 on the tip). `train_derailed` event is emitted either way. One-strike marks are NOT set for declared trains (`_mark_coalesce_derailed` is only called for `_COALESCE_TRAIN_ID_PREFIX` trains).

## 3. How a FAILED MERGE VERIFY's text reaches the next attempt (the shape a screen bounce should reuse)

Workflow-submitted request (`workflow.py::TaskWorkflow._run_merge_phase` loop, `max_merge_retries`):
1. `_run_post_merge_verify` builds `MergeOutcome('blocked', reason='Post-merge verification failed: <summary> [category: X]\n\n<verify.failure_report()>' (+ new-ids enrichment, + skew suffix, + `[main-health probe pending]` note), failure_category, failure_cause_hint, disposition, failure_diagnostic)`. The Future is resolved in `_finalize_inflight` (speculative: in submission order).
2. `workflow.py::TaskWorkflow._submit_to_merge_queue` (11828) reads `result`. Prefix short-circuits first (dropped targets, post-merge equivalence, pyright broken, transient infra, main-health red → `_auto_heal_main_health`, integration_skew); each writes `.task/reviews/merge.json` via `_write_merge_failure_review` and goes to a human L1 or auto-heal. The generic remainder: sets `_last_merge_block_reason`, `_last_merge_failure_category`, `_last_merge_failure_cause_hint`; infers review category (`post_merge_verify` if "verification failed" is in the reason, else `merge_ff_failed` / `merge_error`); `_write_merge_failure_review(category, reason)` (a review-format JSON, reviewer `merge`, severity blocking, full text in `description`); emits `merge_blocked` event (reason[:500], category, failure_category, cause_hint); `_mark_blocked(reason, merge_phase=True, category=category)`.
3. `_mark_blocked` (17129): files an L0 escalation (`summary=reason[:200]`, `detail=reason`), `_ensure_steward_started` (the steward is created lazily only when a pending L0 exists), `_await_steward_completion`. `StewardResolved` → `_requeue()` → `_stamp_merge_retry_pending()` and `REQUEUED`; `StewardReescalatedL1` → human; `StewardTerminalDecision` → honoured. The steward works in the SAME task worktree, so the text it reads is the L0 detail.
4. Back in `_run_merge_phase`: thrash check (`_merge_outcome_signature` vs `retry_ledger.last_merge_outcome_signature`; two equal → `_mark_blocked(escalate_to_human=True)`), `is_ancestor` check, resubmit up to `max_merge_retries`.
5. Re-dispatch path (steward gave the task back, or restart): `_resume_merge_retry_if_pending` jumps straight to merge if `merge_retry_pending.branch_head == HEAD` and the branch still merges cleanly. Otherwise the full pipeline runs. NOTE: `_execute_verify_review_loop` deletes `.task/reviews/merge.json` at its start ("stale merge-failure review"), so on a full re-plan the text survives only in the escalation record, `merge_blocked` event, task metadata (`retry_ledger` signature only) and, if spawned, the dry-run proposal in task metadata (`_spawn_merge_verify_dry_run`, MERGE_VERIFY_RED). I did not find the implementer reading `merge.json` after that delete; unverified whether anything else injects the earlier merge text into the implementer's prompt.

MCP-submitted request: `escalation/src/escalation/server.py::merge_request` returns `{status, request_id, reason: outcome.reason, conflict_details, push_status[, failure_diagnostic]}` (server.py ~4658); the non-terminal poll is `merge_status`, backed by `TerminalOutcomeRecord(reason=...)` in `enqueue_merge_request._on_finalized` retention and the `merge_finalized` event. The text is the same `MergeOutcome.reason`; there is no steward, the MCP caller (an interactive agent or a hand-carry) owns it.

So a screen bounce that returns `MergeOutcome('blocked', reason=..., failure_category=..., failure_cause_hint=...)` through the Future reuses steps 2-5 and the MCP shape with no new plumbing. Choices the lead must make: (i) with a stable `failure_category`/`failure_cause_hint` the signature repeats and two identical bounces escalate to a human (probably wanted for a deterministic defect); leave both empty and the signature falls back to the normalised reason; (ii) a reason prefix added to the short-circuit list in `_submit_to_merge_queue` routes straight to a human L1 (like the drop guard) and skips the steward; without a prefix it takes the steward route; (iii) the `'verification failed'` substring only picks the review category label.

## 6. Worktrees, concurrency, remote host

- A merge-side worktree with the merged tree already checked out exists BEFORE any verify dispatch, for every item kind: `RealMergeItem.merge_wt` (ephemeral `_merge-<hex8>`, created by `GitOps.merge_to_main`, registered in `_owned_merge_worktrees`, HEAD = the merge commit). Chain: `ChainResult.lane` (`_spec-*` pool lane) at `chain.tip`, plus per-link commit SHAs in `chain.links` that can be checked out detached in that lane. Declared/coalesce train: `merge_wt` from `merge_to_main` inside `_do_train_merge`. A 3-30 s check needs no new checkout in any of them.
- Concurrency: one serial merger task and one serial verifier loop; verifies run as background tasks (one per leased host; hosts = local + `laptop`). The merger loop is also where trains run INLINE, and `_deep_chain_placement` runs INLINE on the verifier loop's dispatch path (blocks FINALIZE-HEAD). Anything slow added to those two paths stalls the lane; anything added inside `_run_inflight_verify` (the per-item task) does not.
- Remote (laptop) verify: `_run_post_merge_verify(runner=lease.runner)`; no warm swap; `item.merge_wt` stays on the workstation and is later reused for CAS/rebase. So a screen run by the dispatcher in `item.merge_wt` (or `chain.lane`) before `pool.dispatch` is host-independent. I did not trace how the sha reaches the laptop (git remote `leo-laptop`, immutable gate checkout, task 6565); not needed for placement.
- Environment caution (not measured): the scanner imports `shared.*` (`scripts/inline_suppression_refusal.py` says run it as `uv run --project shared python scripts/inline_suppressions.py`). From the dispatcher, `shared` resolves to the dispatcher's own checkout, while `scripts/inline_suppressions.py` and its baseline come from the merge tree. A branch that edits the scanner or the baseline is judged by a mixed pair unless the screen also runs the scanner from the merge tree under that tree's `shared`. Use the same env scrub as verify (`orchestrator/src/orchestrator/verify.py::_target_subprocess_env`, per CLAUDE.md).
- Observed chain build cost (rule: runs.db `events`, merge_verify, `chain_items >= 2`, n=2, to 2026-10-29T18:31Z): `chain_build_ms` 6906 (2 links) and 31038 (1 link); verify durations 2,844,556 ms and 1,013,132 ms. A screen of ~8 s per link is the same order as the build and about 0.3-0.8% of the verify.
