## A4. "Failures not present on main": how the subtraction works and what it permits

- **Baseline source:** `verify.py::main_baseline_failing_ids(config, module_configs, git_ops, main_sha, red_module_prefixes=...)`. Cache-first (`_BASELINE_FAILING_IDS_CACHE`). On a miss it probes bare main in a `_mainprobe-` ephemeral worktree, per red module (task 5627), or the whole tree. A passing merge+full gate SEEDS `seed_main_baseline(merge_sha, frozenset(), skipped=...)` in `merge_lane/worker.py::_run_post_merge_verify`, so in steady state a green-landed sha is a cache hit with an empty failing set.
- **The failing set of a known red does feed it:** that cache IS the red verdict's failing set. `verify_failure_is_preexisting_on_main` uses it first (task-mu fork): if `failing_result.failing_test_ids` is not None, `is_wholly_preexisting(branch_ids, baseline)` then `_wholly_preexisting_after_flake_gate` -> `(True, main_sha)` (MAIN_RED). Otherwise `partition_new_failing_ids`: any id main RAN green means task fault `(False, '')`; only-skipped ids defer to the legacy `(category, cause_hint)` signature probe.
- **It never turns a fail into a pass.** In `_run_post_merge_verify`, `if not verify.passed:` always returns a blocked outcome (or a flock / unscoped / ENOSPC / infra variant). The subtraction only chooses `MAIN_RED` vs task-fault and the reason wording. The one pass-side use of the baseline is the opposite: it can WITHHOLD (trivial-pass gate). Under `merge_verify_breadth: "full"` (yaml line 1572), every merge gate runs every registered module, so any verify on a red base reproduces the red.
- **Consequence for S1.2:** a verify started on a known-red base fails with near certainty for non-fix items. Only two classes can legitimately pass: (a) a fix-forward item (A5), (b) a "red" that is a flake (the baseline is one UNRETRIED run; the isolated-rerun flake gate downgrades the verdict, but the baseline entry STAYS red until main moves: the `known_failing_ids_on_main` docstring says so).

## A5. Fix-forward hazard: how a task that fixes the red is identified

Existing structured fields:
- `metadata.merge_lane == 'high'`, `metadata.spawn_context` in `main_health_fix_owner.py::FixSpawnContext` (`main_health_auto_heal` or `main_health_fix_filed`), `metadata.main_health_signature` (sha-independent signature, `MainBreak.signature` = `RetryLedger.compute_merge_outcome_signature`), `metadata.main_health_escalation_id` (only when an L1 exists). All are written by `main_health_fix_owner.py::build_main_fix_task_arguments`.
- `MergeRequest.lane: Literal['normal','high']` (`merge_lane/types.py::MergeRequest.lane`), set from task metadata at `workflow.py` (`lane=lane_for_task_metadata(self.task.get('metadata'))`). The merge worker sees THIS, not the task metadata.
- The lookup `find_tasks_by_metadata(key='main_health_signature', value=sig, statuses=ACTIVE)` finds the open owner (`MainFixTaskFiler._find_open`). Async task-store read.
- `FixOwner(signature, task_id, filed, spawn_context)` is the in-process result.

Exempting by an existing structured field, not string parsing (heuristic 12):
- **Narrowest and precise:** the request's task metadata `main_health_signature == verdict.signature`. The worker does not hold task metadata for a `MergeRequest`; it would need a new field on `MergeRequest` stamped by the workflow, or a task-store read per verify start.
- **Available today, coarser:** `req.lane == 'high'`. Already honoured by the lane machinery (`_pop_next_pickable` iterates `high` before `normal` and skips only a halted lane; `chain_snapshot` the same). It also covers operator `merge_relane` and any task the operator put on `high`, so the exemption is wider than "fixes the red". `offline_lane_filing.py::MERGE_LANE` is `'normal'`, so offline-lane tasks are not exempt.
- **Do not key on the reason prefix** (`MAIN_HEALTH_RED_REASON_PREFIX`) for a new guard: that is the string protocol the current consumers use; heuristic 12 says not to extend it.
- **Not lane-bound:** direct human commits to main (like `6279723661`, 09:08Z) bypass the lane entirely and are unaffected by any lane guard.
- **Wedge risk if there is no exemption:** a guard that refuses every verify on a red sha, with the only fixer a normal-lane item, stops main from ever moving. The trivial-pass gate documents the same wedge ("main must be greened by a code-touching merge or operator action"). A declared train whose union IS the fix (the 3997 shape: members red alone, green together) sits on a green base, so it is fine; a declared train that repairs a red base would need the same exemption.

## A6. Where a guard would plug in; narrowest keying; failure modes (map and propose; the lead decides)

**Candidate plug points, per path** (only existing structured values):

| Path | Function / seam | Existing value to check | Existing precedent for "do not start now" |
|---|---|---|---|
| Slot 1 and slot 2 | `_dispatch_item`, in the pre-dispatch block next to the operator-halt / admission-halt check | `known_failing_ids_on_main(await get_main_sha())` and `item.request.lane` | `InflightStatus.REQUEUED_PREDISPATCH` via `_requeue_request`. **Caution:** the halt case does not spin because the merger loop waits on a resume signal; a red guard needs the same wait or it loops dequeue -> merge -> requeue |
| Slot-level, upstream | `_pop_next_pickable` / `chain_snapshot` | `is_lane_halted(lane)` | an existing, event-gated wait (`_wait_until_any_lane_runnable`), with `high` already exempt. The existing halt sets it, but only `compile_error` reaches `halt_lane` today (A1) |
| Chain tip | `_deep_chain_placement` | same | returning `None` falls back to the item's own adjacent verify, which is itself a verify on the red base. A chain-only guard is NOT sufficient; it must sit at `_dispatch_item` |
| Declared / coalesce train | merger loop train branch, beside `if self.is_admission_halted: await self._stand_down_train(req, actual_main)` | same | `_stand_down_train` |
| Solo / gate re-verify | `gates.py::_reverify_rebased_tree` entry | same | none |

**Narrowest keying (proposal):** "the base sha equals the sha of a red verdict that has not cleared". Two candidate verdict carriers:
- **K1, exists:** `known_failing_ids_on_main(main_sha) != frozenset()`. Pure, sync, cache-only, sha-keyed, with one precedent consumer. Semantics are "known failing at that sha" (a lower bound). It is populated by ANY baseline probe, not only by a confirmed verdict, and it is NOT flake-confirmed.
- **K2, new:** a worker-held record written where the verdict is confirmed: in `_run_deferred_main_health_probe` after the `probe_sha == get_main_sha()` check (just before `auto_heal`), and from the sync consumers (`_do_train_merge` / `_derail_on_train_verify_failure`, which have the worker). Shape: `(main_sha, MainBreak.signature, fix_owner_task_id)`. Flake-confirmed by construction (it runs after the confirm gates). This capability does NOT exist today and the PRD must name it as new (gate G3).

For slot 2 and chains, the key is the REAL main sha (`await self._git_ops.get_main_sha()`), never `item.base_sha` (which is an unlanded speculative commit).

**Failure modes:**
1. **Wedge.** Refusing everything on a red sha stops main moving. Needs a fix-forward exemption (A5) and an expiry (TTL or "re-probe once the sha is older than T").
2. **False red persists.** K1 stays red until main moves even when the isolated re-run proved the verdict a flake. With the guard stopping the lane, main may never move. K2 only records post-confirm verdicts, which cuts this.
3. **The verdict is late.** The probe is detached (deferred mode) or inline on the merger (sync mode, 2 h 35 min observed on 6057). Verifies dispatched in that interval run unprotected, and no existing path aborts an in-flight verify on a red verdict. The guard prevents only the verifies AFTER the verdict.
4. **Restart.** K1, K2 (if in-memory), the lane halt and `auto_heal_registry` are all process-local. After a restart the guard fails open: one wasted verify per restart per red sha. Fleet restarts occur at most every ~72 h by the coordinator (yaml line 1495) plus drains.
5. **Direct commits.** A human fix on main (`6279723661`) changes the sha, so a sha-keyed verdict correctly stops applying; the new sha is unknown to K1, so the guard fails open. A wrong "still red" is bounded by the sha comparison.
6. **Only some categories are real fixes.** Deciding whether `lint_error`, `type_error`, `test_failure` reds should halt/hold is a policy change: `is_auto_heal_eligible` deliberately limits halting to `compile_error` ("test_failure: multi-file; needs human judgement"). Extending the existing halt to all categories is a different decision from adding a lighter "do not start" gate.
7. **`lane == 'high'` is broader than "fixes the red"** (A5): an exempt non-fix item just burns one verify.

## B8. Branch ref spelling, `_run` rc, "fail loudly", reproduction

**Spelling.** The branch of task `<id>` is `task/<id>` (`config.branch_prefix`, default `'task/'`, `config.py::GitConfig`). It is built in many places as `f'{self.config.branch_prefix}{id}'` (about 20 sites in `git_ops.py`). The canonical single sources are:
- `shared/src/shared/branch_names.py::canonical_queued_branch_name(branch, branch_prefix)`: pure string, idempotent ("prepend unless already present").
- `merge_lane/types.py::QueuedBranch.parse(raw, branch_prefix)`: `.full_name` is the git ref, `.bare_id` is the bookkeeping key. Its docstring says "Git refs should always be built from `.full_name`" and not to add further ad hoc prefix sites.
- `git_ops.py::GitOps.resolve_queued_branch_ref` (async, git I/O, returns None if absent).

**Where the bug is:** `get_changed_line_ranges(ref)` interpolates its argument raw: `git diff {main_branch}...{ref} --unified=0 --no-color` with `_, diff, _ = await _run(...)` (rc and stderr discarded), then `parse_diff_line_ranges(diff)`. Both callers pass a bare task id: the worker passes `c.task_id` (it holds `c.branch.full_name` and does not use it), the workflow passes the bare ids.

**`_run`:** `git_ops.py::_run(cmd, cwd=None, *, input_text=None) -> tuple[int, str, str]` returns `(returncode, stdout, stderr)`. It does NOT raise on a nonzero rc; it raises only `WorktreeMissing` (missing cwd) or `FileNotFoundError` (missing binary). Hence the `{}` on failure.

**Reproduction** (`git clone --shared` of the main checkout at `/tmp/stream1-C2/clone`, HEAD `8e866e120e`; commands run read-only there):

| Command | rc | stdout | stderr | Reading |
|---|---|---|---|---|
| `git diff main...5925 --unified=0 --no-color` | **128** | 0 bytes | `error: short object ID 5925 is ambiguous` + 5 candidate commits (`59250b1a75`, `592549f4d2`, `592568232d`, `5925756a23`, `59257f6ed7`) | `get_changed_line_ranges('5925')` returns `{}` ("touches nothing", i.e. "stackable") |
| `git diff main...5563 --unified=0 --no-color` | **0** | 3455 bytes | empty | silently resolves to the unrelated commit `5563a70ca592...` ("test(census): RED ... task 5592 step-1", 2026-09-27). `git rev-parse --verify 5563` (no `...`) reports the ambiguity and lists 15 candidates (1 commit, 9 trees, 5 blobs); the `main...X` form only needs a commit-ish, and exactly one candidate is a commit. Files in the diff: `dashboard/tests/test_census.py`, `tests/scripts/test_dashboard_task_vocab.py` |
| `git diff main...task/5563 --unified=0 --no-color` (after fetching `task/*` heads into the clone) | 0 | 66160 bytes, 119 hunks | empty | the real branch (tip `0006c35f6e`) |
| `git diff main...task/5925 ...` | 0 | 11761 bytes, 26 hunks | empty | the real branch (tip `dd82fa5e89`) |

So the wrong-ref result is `{}` for 5925 and a wrong 2-file range set for 5563, vs 119 and 26 hunks for the real branches.

*Rule:* one invocation per row in the clone, `--unified=0 --no-color` as in the method; "bytes" = `wc -c` of captured stdout; "hunks" = count of lines starting `@@`. Ambiguity depends on object-name abbreviation in THAT repo state (the clone at `8e866e120e`); on a different object database the candidate set can differ.

**Design options for the fix (SPOT):**
- (A) Canonicalise INSIDE `get_changed_line_ranges` with `canonical_queued_branch_name(ref, self.config.branch_prefix)`. Single site, fixes both callers, and is idempotent so the existing tests that pass `'task/123'` / `'task/b3_anchor'` keep passing. Caveat: a request whose `branch` is not a `task/` name (`QueuedBranch` handles "full non-task name") would be mis-prefixed if it were passed as a bare name.
- (B) Callers pass the full ref: the worker already has `c.branch.full_name`; the workflow would build `QueuedBranch.parse(cid, prefix).full_name`. Needs both call sites changed and leaves the method's contract ("any ref") implicit.
- Optional hardening: diff against `refs/heads/<full ref>` so a tag or abbreviated id cannot match.
- `GitOps.stack_train_branches` already rebuilds `f'{branch_prefix}{member_id}'` for the same members, so (A)'s task-id convention is the same one the train code assumes.

**"Fail loudly" for callers.** Both callers `asyncio.gather` the calls, so a raise propagates to the caller of the whole pass:
- `workflow.py::_maybe_form_train` runs inside `_run_merge_phase` via `_maybe_defer_as_train_member`; an uncaught exception there reaches the workflow's merge-phase error handling. There is no local try/except. Decide: raise vs "treat a failure as NOT stackable", the fail-closed direction. The current `{}` is the fail-OPEN direction (every pair "stackable").
- `worker.py::_stack_coalesce_train` is called from `_maybe_coalesce_waiting_singles`, which is called in the merger loop (`if self._speculation_controller.can_coalesce(): await self._maybe_coalesce_waiting_singles()`). It sets `_last_coalesce_signature` BEFORE the stack attempt (documented DD3), so a raise leaves the set debounced until composition changes.
- Both are unreachable once the two flags are off, so the loud-failure shape is a design choice without a live consumer. `workflow.py::_select_train_members` itself already treats a missing id as `{}` (`ranges_by_id.get(candidate_id, {})`), another place where "unknown" collapses to "stackable".
- **Gotcha, ratchet:** `merge_lane_ratchet_baseline.json` pins `get_changed_line_ranges` at cognitive complexity **0**. An `if rc != 0: raise` inside it adds 1 and raises the measure. `orchestrator/tests/test_merge_lane_ratchet.py` fails on any raise unless authorised with `scripts/merge_lane_metrics.py --write-baseline ... --authorize-raise <task> --reason ...` (adds a file under `orchestrator/tests/merge_lane_ratchet_raises/`). A new function absent from the baseline only meets the ceilings (cognitive 15 per function), so extracting the rc check into a new helper avoids the authorised raise. The same ratchet covers `merge_lane/worker.py` edits. The review-all report `plans/review-all-dark_factory-20261008.md` lines 653-657 already records the rc-discard pattern across 11 `GitOps` methods; an S1.3 fix limited to this method is the narrow slice.
