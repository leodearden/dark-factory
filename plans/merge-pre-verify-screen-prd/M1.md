## 5. Reading for gate G6 (premise validity), by the lead's three S1.1 questions

1. **Does the premise hold?** Yes, strongly, for the ratchet: C1 alone is the first failing check of 34.0% of all failed merge verifies (50 of 147), 33% pre and 45% post, at 8 s cost and 0 false alarms in 60+ sampled green verifies. The rate has not changed with the chain_cap flip. The task-role verify does not run it unless the diff touches `scripts/**`, no hook runs it, and no agent instruction mentions it. In 49 of 50 cases the item tip alone already fails it.
2. **Which checks belong in the screen?** C1 is the case. Seven checks (T0) at under 10 s CPU each, about 25 s together, reach 39.5%. The step from T0 to T1 (7 more checks, 14-31 s each) buys 8.8 points for about 135 s more; T2 another 8.2 points for about 180 s more. C3 needs the byte-equality form, not `--check`. C13/C13b/C19 depend on state outside the tree and must stay out. C7 and C10 only ever fired on a red base, so they belong in the base check (S1.2), not the item screen.
3. **Chain per-link motive.** Not measurable live: 2 chain-tip verifies in the window, both green, 0 red. Proxy rule: p = distinct tasks with a C1 own-defect verify (42) over distinct tasks with any `merge_verify` row (444) = 9.5% (post: 5 of 48 = 10.4%). If links were independent, a chain of L links carries at least one C1-defective link with probability 1-(1-p)^L: L=2 18%, L=3 25%, L=6 45%. This overstates the live risk if the deep-merge head selection already skips branches that were recently blocked, and understates it because train members and resubmits are not in the denominator. Treat as a prior, not a measurement.

Things the lead may want to weigh against the premise:
- The screen's value is bounded by what the lane does after a screen failure. A screen failure that re-pends or blocks the item costs the same escalation traffic as the verify failure it replaces; only the host time (24.7 h for C1) is saved.
- 4 of the 54 C1-red verifies were speculative children of a red parent. A per-link screen would catch the parent at the parent's own screen; for children the screen needs the base-first rule of 2.5 or it would blame them.
- Train former (coalesce) goes OFF by ruling; 18 of the 147 failures (17 unions + 1) disappear with it, and 7 of the 50 C1 own-defect catches were train unions, so the figures above include some that will not recur. Restricted to the 129 non-train failures: C1 43 (33.3%); T1 58 (45.0%). Rule: the same reproduction results restricted to kind != train.

## 6. Could not verify or caveats

- Host load: all timings were taken at load average 80-440 on 32 cores. CPU figures are the usable ones; the first-run ("cold") numbers are not true cold-cache numbers.
- Reproductions use the pinned clone's `.venv` third-party packages with `PYTHONPATH` set to each checked-out tree's package sources. A check whose result depends on a third-party version change inside the window would not show; none did (0 misses).
- Member reproductions use current branch tips (may postdate the block); misses there are inconclusive, hits are conclusive. Done members were reconstructed from `merge_sha^2` of their landing, which is the landed tip, possibly rebased.
- Per-leg timing exists only for local verifies from 2026-10-22; 30 of 83 caught verifies. Laptop (remote) summaries carry no timing and no leg name, so "first failing leg" for them is derived from the failing test's module and plan order (validated 36 of 36 where logs exist).

- C2's file did not exist on older shas, so its pass-sample false-positive check is 8 applicable samples. C1 has 60, C3 20.
- Data is a live DB: rows after 2026-10-29T17:40Z (one more failed verify by 20:09Z) are excluded. Main moved after `07bd68fd99` (now `b137525653`); timing and reproductions use the pinned sha only.
- I did not run any candidate across the full main history (only C1 was sampled, 261 commits); other candidates' "red on bare main" evidence is the base-of-failed-verify reproduction, i.e. episodes, not rates.
- The brief said "cite code as path::Symbol". I cited tests and scripts by path and function name; line numbers are not used.
