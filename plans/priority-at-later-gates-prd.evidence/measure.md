# Merge-pool measurements (read-only, from the per-project runs.db event stores)

Generated by /tmp/prd-merge-pool/measure/*.py (s12.py items 1-2, s34.py items 3-4, s567.py items 5-7, verify.py re-check, mk.py assembly). All sqlite opens are `file:<path>?mode=ro`; every events query is bounded by timestamp.

## Conventions and hazards read this first

- Units: seconds unless stated. Percentiles are linear-interpolation (numpy "linear"). n is given for every row. Everything below is MEASURED from event rows unless a line says "approximation" (only item 5's same-head proxy, item 5's cause regexes, and the item 6/7 reconstructions are rule-based reconstructions, labelled where they appear).
- Windows are as specified. dark-factory "recent" (10-30..11-13T12) CONTAINS "paused" (11-09T14:13..11-13T12) and overlaps "earlier" (10-25..11-08T16) from 10-30 to 11-08, so the three are not independent samples. Other projects: 10-11..11-08T16 only.
- A coalesced-TRAIN era exists in dark-factory data, roughly 10-30..11-01 (events train_started/train_coalesced/train_merged/train_derailed; none in the paused window and none in the other projects' windows). In that era (1) a train's union verify is logged as a `merge_verify` with chain_items=1 and speculative=null although it verifies 2-3 requests; I corrected its k to the train's member count (passed: merge_sha equals a train_merged.merge_commit_sha; failed: a following train_derailed whose reason starts "Train union verify failed" for the same head task with no other merge_verify of that task in between). Item 4(a) also prints the LITERAL rule (no correction) so the two are not confused. (2) Requests absorbed into a train are finalized `superseded` (superseded_by=coalesce-*) with no dequeue, and the train's own queue entry is dequeued and finalized with NO merge_queued event (orphan dequeues/finalized). So items 2 and 7 are least reliable for 10-30..11-01; the paused window (post-train, chain era) is the cleanest sample.
- Gate re-verification rows are identified exactly, not by proxy: a merge_verify whose merge_sha equals the merge_sha of an earlier merge_reverify_gate event of the same task. 229 of 840 recent-window DF verifies are such rows. The runner_reason=gate_on_head_host proxy catches only 70 of them (it and base_relation only exist from about 11-07), so use the sha join.
- merge_verify wall = data.duration_ms (the events.duration_ms column is null). Verifies cancelled mid-flight (`merge_verify_cancelled`, 52 in DF recent) emit no merge_verify, so walls are for completed verifies only.
- `merge_dequeued` is the queue pick; the request is verified afterwards. `merge_dequeued.data.queue_depth` is ~0 even when 6+ requests wait, so it is not a waiting-set size (see item 7).
- Verification: verify.py recomputed items 1, 2(a), 2(b) (all projects/windows, plus item 1 by tier for dark-factory) with SQL json_each/julianday/window-style joins on an in-memory copy of the rows, and item 4 counts (single and batch n and passed, gate and train identification by SQL), and compared with the figures here: 41 comparisons, 0 mismatches. The stores are live (dark-factory events were still arriving), so a rerun after 2026-11-13T15:45Z can differ in the last digits of windows that end at 11-13T12:00 only through late-finishing episodes.
- solar-challenge and solar-challenge-platform both have exactly 1365 granted task-role legs in item 1; that is a coincidence (different plan ids, different waits), confirmed by a separate json_each count on each db.

## Item 2. Wait in the merge queue (two rules, never joined)

Episode = a task's first `merge_queued` after its previous `merge_finalized` (any state) up to its next `merge_finalized`. Episodes are assigned to a window by that first merge_queued time. Event replay starts 45 days before the window and ends 3 days after, so waits that finish after the window are included. Measured.

- (a) first merge_queued of the episode -> first `merge_dequeued` inside the episode. Population = episodes that were dequeued; episodes never dequeued are counted by final state in the header line (they have no pick wait). Waits of episodes still open are not included.
- (b) first merge_queued of the episode -> its `merge_finalized` with state done (includes the verify and landing time, not only queueing). `(b-field)` is the event's own `queue_to_land_secs` for the same episodes; it is populated only from about 11-09 (n shown), and where populated it equals (b) to the second.
- (a2) is the gates.py pairing (each dequeue vs the earliest unmatched queued since that task's previous dequeue/finalize); it agrees with (a) within 1 row.
- (a) and (b) are NOT comparable: different end events, different populations (b is done-only). Neither includes the time between a `superseded` finalize and the task's next episode (median ~3.6 days in DF, so the episodes are not joined).
- Tier (dark-factory) = scheduler tier at the first merge_queued, same lookup as item 1.

## Item 3. Merge verify wall time

Rule: `merge_verify.data.duration_ms` / 1000, rows with timestamp in the window, runner `history-leg` (1 row) excluded, grouped by `data.runner`, `data.passed`, and k = `chain_items` (null counted as 1) corrected for trains as described above. Bucket table includes gate re-verifications (they are single-request verifies); the slope fit excludes them and uses passed verifies only (a failed verify may stop early). Fit: wall = a(1 + s(k-1)) by ordinary least squares of wall on (k-1), s = slope/intercept, bootstrap 2000 resamples of rows for s p5/p50/p95, plus the per-k median ratio s_k = (median_k / median_1 - 1)/(k-1). Two variants per runner: chains+trains pooled, and speculative chains only. Measured; the fit is thin (n with k>=2 is 18-32 per runner, k=4 has 2 rows, local has no k=4), so treat s as "indistinguishable from 0 within about +-0.03", not as a value. Runners seen: laptop, local (and history-leg, excluded). Runner is chosen per verify (`runner_reason`), so laptop vs local walls also differ by host speed (about 2x).

## Item 5. False-failure proxy (dark-factory)

Population: failed (passed=false) merge verifies with k == 1 after the train correction (so train union failures are not counted), timestamp in the window; shown for all of them and again excluding gate re-verifications. For each, take the same task's NEXT merge_verify (any later event id, from the same task, looked up to 3 days past the window).
- "Same head, no new commits" is not on the event. Approximation R1 (the rule you specified): the next verify passed, is a single, and the task has no `task_started` and no `phase_enter` event between the two verifies (task never went back to an agent phase).
- Approximation R2 (stricter): R1 and additionally no `invocation_end` event for the task between them, except `unblock_auto` dry-run invocations (steward and merger invocations count as an agent touching the branch). R1 alone mostly counts cases where a steward agent ran (it can commit a fix without emitting task_started/phase_enter), so R1 is an upper bound on false failures and R2 is closer to a lower bound.
- Weaknesses of both: the merge worker rebases onto a moved main between attempts (head sha changes without an author commit; it is not detected), a human can commit from outside the orchestrator with no event, and a pass after a fail may be a real fix. The next verify's merge_sha equals the failed one's in only 2 of 65 cases (it is a freshly built merge commit), so sha equality is not usable. A denominator row "no later verify observed" means no later verify of the task exists in the store (task cancelled, parked, or still blocked).
- Infrastructure/timeout cause: the failed verify's following `merge_finalized.reason` (before the task's next verify) is classified by prefix: infrastructure = starts with 'Merge worker shutting down', 'Transient infrastructure failure', 'Verifier error', 'advance_main deferred', 'Post-merge verification blocked: flock contention', or carries `[category: infra_timeout]`; main-red = regex 'Main-health red|reproduces on bare main'; everything else 'other'. An earlier full-text regex (timeout, ssh, connection, ...) was rejected because it matched words inside test output. The verify's `units[].outcome` only ever holds ran_green/ran_red, so units carry no timeout signal. The system's own `merge_attempt.disposition` (branch_bug / integration_skew / none) for the same failure is shown as an independent label. Unmatched = the failure has no finalized before the next verify (train derails and such).

## Unknowns

- The branch head at the time of each failed verify is not on any event, so "same head, no new commits" (item 5) is only bounded between R2 (lower) and R1 (upper); no exact false-failure rate was determined.
- Whether a `merge_dequeued.data.queue_depth` of ~0 means a different queue (it is not the waiting set); and why `merge_heartbeat.data.depth` is about 3 to 3.5 above the reconstructed waiting set (in-flight requests? requests re-entering without a merge_queued event?) was not established. The merge wait figures for 10-30..11-01 are distorted by trains (hazards section) and could not be repaired exactly; the paused window is the clean sample.
- Item 2(a) has no value for requests that were never dequeued (finalized blocked/superseded/done straight from the queue); their queue wait is unmeasurable from these events. Item 6's distribution omits requests never re-queued (censored counts printed), so its tail is a lower bound.
- The per-extra-member slope is statistically thin (see item 3); in particular there are no k=4 local rows and no chain verifies in the other projects (chain_items is 1 or null there), and the plan's note that depth >= 8 is unmeasured still holds (no k>=7 row exists).
- Verify-admission waits are per module leg, not per task; no per-task total (sum or max over a task's legs) was computed. The queue-pick tier for waits is the dispatch-time `lock_acquired` priority, which for tasks resumed or hand-carried may not equal the tier the scheduler applied to the merge (a `unknown` tier exists for tasks with no priority-carrying lock_acquired since 2026-08-15).
- Other projects' schedulers were halted 11-08T16:04Z; their later merge events were not used, and I did not check whether their pre-halt windows were representative (reify's blocked/done ratio is dominated by 'Merge worker shutting down' blocks).
- `merge_verify_cancelled` verifies (52 in DF recent) have no completed wall, so item 3 and item 4 exclude them; how many were cancelled for tip adoption vs other causes was not analysed.
