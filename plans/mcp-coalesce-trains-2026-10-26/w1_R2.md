# R2

Today 'merge-deferred' is a status that only a TaskWorkflow can enter, and the whole train contract rests on it. Table A allows exactly one edge into it, in-progress to merge-deferred. fused-memory's shipped config enforces Table A (enforce_transitions: true), so pending, blocked and deferred tasks cannot be parked there by anyone. A parked member holds no module lock and no claimant: _run_slot's finally clears both. It is kept alive only by lane custody, a live single merge request in InFlightMergeRegistry, a live claimant, a pinning escalation, or an active declared-train peer. AbandonedMemberSweep re-drives a member that shows no owner on two consecutive passes of the 900s stranded-reconcile service, with a 900-1800s latency. The re-drive always writes pending, or done when the branch is already on main. It never restores a prior status. Every status-flip callback (mark_member_done, redrive_member, _revert_withheld_member) is written for members that sit at merge-deferred. status_check treats any other real status as train_incomplete and synthesises 'merge-deferred' only for ids with no task row. A coalesce train resolves each absorbed single's future 'superseded' before the train starts. Nothing re-submits an absorbed request whose task never parked, so a naive admission of MCP singles recreates the pre-4953 stranding. A lane-owned park-and-restore design hits three structural walls. First, Table A has no pending/blocked/deferred to merge-deferred edge, and no merge-deferred to in-progress or deferred edge. Second, leaving 'deferred' atomically deletes metadata.deferral, a write-authority-protected record that can be re-created only through set_task_status(status='deferred', deferral=...). A held_by_session record also needs a live `claude` pid on the same host. Third, set_task_status has no expected-from-status guard, so a restore can clobber a human's concurrent change. Several parked-state consumers silently drop signals meant for the original status. An L2 'resume' resolution is skipped for merge-deferred rows, the landed-outbox reconciler prunes without a done-write for preserve statuses, and the sweep's re-drive turns a human hold into pending and so makes the task dispatchable. The status flip for MCP singles that land solo is currently the submitter's job (set_task_status done after merge). A lane-owned flip would need to coexist with that.

A parked, absorbed member therefore has NO live workflow, NO claimant and NO module locks.  — `orchestrator/src/orchestrator/workflow.py::TaskWorkflow._enter_merge_deferred`

## 7. What an MCP single's task status actually is today
- [read] MCP merge_request builds MergeRequest without awaited_by_workflow; it does not touch task status at all (reads task metadata only for the degeneracy probe and lane fallback). Callers stamp done themselves (set_task_status done with done_provenance) after merge_status shows done.  — `escalation/src/escalation/server.py::merge_request`
- [read] Typical MCP-single statuses: blocked (release_workflow parks an in-progress /unblock task there; the final done is blocked->done), deferred with held_by_session (a pending task the /unblock session holds so the scheduler cannot dispatch it into the worktree being rebased; done is deferred->done), carried_by (merge moved to a separate carrier), pending or in-progress orphans, or merge-deferred when a human walks a carrier in-progress -> merge-deferred and submits (OPERATIONS.md).  — `skills/unblock/SKILL.md::Release the orchestrator's grip`
- [read] skills/merge-queue tells submitters that, after absorption into a coalesce train, a non-done status (pending / merge-deferred / anything else) is a veto on self-stamping done: wait for the orchestrator's automatic flip, and stop at 20 min as landed-but-not-credited. A lane-owned done flip for MCP singles would need to be reconciled with the submit protocols that still say 'update the task: set_task_status done' on a plain done.  — `skills/merge-queue/SKILL.md::2v. The veto (both arms)`

## HAZARDS
- **(a) Naive admission, ANY status S in {pending, in-progress, blocked, deferred}: the train fails the status pre-check and the absorbed MCP single is stranded, with its caller told 'superseded'.** — _stack_coalesce_train resolves the single's future 'superseded' and retires its lane item BEFORE the train runs. The task row is still S (no TaskWorkflow parks it), so _do_train_merge step (a) sees status != 'merge-deferred' and returns train_incomplete 'blocked'. _unwind_coalesce_train restores pre-stack tips; MemberRedriver.redrive reports NOT_PARKED for a non-merge-deferred row and writes nothing; no code resubmits it; one-strike marking then bars it from re-coalescing. The submitter polls a superseded successor that never lands. This is the pre-4953 failure the awaited_by_workflow gate exists to prevent. — `orchestrator/src/orchestrator/merge_lane/worker.py::SpeculativeMergeWorker._stack_coalesce_train`
- **(a) Naive admission, no task row or task_id != branch: members are keyed by the MCP-supplied task_id, not the branch.** — MergeRequest.task_id comes from the independent task_id parameter, and stacking uses branch_prefix + task_id. A task-less id is synthesised 'merge-deferred' by status_check and no-op'd by mark_member_done/redrive_member, so the train lands but nothing credits or re-drives it. A mismatched task_id would make the callbacks probe and flip an unrelated task's row (X->done edges all exist) while the real branch's task is untouched. — `orchestrator/src/orchestrator/harness.py::build_train_callback_factory`
- **(a) Naive admission, pending: a pending MCP single is dispatchable while the lane stacks and rewrites its branch.** — Scheduler._eligible_for_dispatch dispatches any pending task without a live claimant. Nothing marks 'an MCP request is in flight' for dispatch. A fresh TaskWorkflow could start in the same task branch/worktree while stack_train_branches rebases it onto a predecessor, or while the train lands it. skills/unblock holds a pending task as deferred (held_by_session) precisely for this reason. — `orchestrator/src/orchestrator/scheduler.py::Scheduler._eligible_for_dispatch`
- **(a) Naive admission, in-progress with no live claimant (orphan): the stranded sweep can re-pend it mid-train.** — TaskGroundTruth._resolve_live_claimant considers only is_actively_held, a fresh DB claimant and a live plan.lock. A live MCP merge request or train custody is not a signal, so _reconcile_one_stranded (REVERT_TO_PENDING for an off-main branch with no pin) writes pending under the train, after which dispatch could race the lane. — `orchestrator/src/orchestrator/task_ground_truth.py::TaskGroundTruth._resolve_live_claimant`
- **(a) Naive admission, blocked: the stranded-blocked redispatch and the sweep act on the task while its merge is in flight.** — With no live claimant and no pinning escalation (e.g. the L2 resolved before merging, a hazard the code itself names), Scheduler._phase_redispatch_stranded_blocked re-pends it, or the harness blocked arm marks it done on landing evidence. The train's own mark_member_done may then collide, or a human's block is silently released. — `orchestrator/src/orchestrator/scheduler.py::Scheduler._phase_redispatch_stranded_blocked`
- **(a) deferred: the lane cannot flip or park it without destroying the hold, and a done flip bypasses the carry protocol.** — deferred->done is legal, so a mark_member_done on a deferred member succeeds and leaves no deferral_cleared audit by a human; but the lane cannot park it (no deferred->merge-deferred edge) and the pre-check rejects it anyway. If it ever did become merge-deferred, the exit clears metadata.deferral irrecoverably (Exit.clear_keys), and re-entry requires a freshly validated record with a live `claude` holder pid. — `fused-memory/src/fused_memory/middleware/deferral_gate.py::plan_status_change`
- **(b) Lane parks pending/blocked/deferred as merge-deferred: the write is illegal today.** — Table A has exactly one inbound edge to merge-deferred (in-progress). With enforce_transitions true the interceptor returns illegal_transition and Scheduler.set_task_status raises SetTaskStatusRejected. The design needs new Table A edges (pending/blocked/deferred -> merge-deferred) or a different holding state, and edge changes cascade into fused-memory enforcement, recon's actor subset and the OPERATIONS.md statement that Table A refuses merge-deferred -> deferred. — `shared/src/shared/task_transitions.py::_UNION`
- **(b) Restoring deferred or in-progress is impossible with today's edges, and restoring any status is an unconditional overwrite.** — merge-deferred has outbound edges only to done, pending, blocked, cancelled. A restore to deferred also needs a fresh deferral record that cannot be minted by the orchestrator for held_by_session (the holder must be a live `claude` pid). Scheduler.set_task_status has no expected-previous-status guard, so a restore overwrites whatever a human wrote while the member was parked (for instance a human cancelling or re-pending). — `orchestrator/src/orchestrator/scheduler.py::Scheduler.set_task_status`
- **(b) Parked blocked task: operator resolutions are lost or rewrite the parked row.** — An L2 'resume' resolved while the member is merge-deferred is DEBUG-skipped (_RESUME_REPEND_STATUSES = {blocked, in-progress}), so the authorisation to re-pend disappears with the closed record; 'close_only' drops the pin so the sweep can re-pend it. 'restart/park/abandon' overwrite any non-terminal status, including a train member, so the train goes train_incomplete. A restored blocked also fires targeted reconciliation (STATUS_TRIGGERS includes blocked) and charges the park-stop counter. — `orchestrator/src/orchestrator/harness.py::Harness._cascade_unblock_member`
- **(b) Any parked member that is later 'recovered' by existing paths comes back as PENDING, not its original status.** — AbandonedMemberSweep, redrive_member (not-on-main), _revert_withheld_member and _unwind_coalesce_train all write pending. For a blocked or deferred origin that turns a deliberate hold into a dispatchable row: the scheduler can then start a fresh TaskWorkflow inside the human's worktree (the exact hazard skills/unblock names for pending tasks). Every one of these recovery writers would have to be taught to restore from a recorded origin status. — `orchestrator/src/orchestrator/merge_deferred_recovery.py::AbandonedMemberSweep`
- **(b) Ownership signals vanish at absorption, so the parked member looks abandoned.** — InFlightMergeRegistry releases the slot when the single's future resolves 'superseded', so SINGLE_REQUEST ownership ends. A lane-parked member with no workflow, no module locks and no claimant is held only by TRAIN_CUSTODY (and a pin or claimant if present). Between a derail/crash and the restore the sweep treats it as NONE and after two passes (900-1800s) re-drives it to pending. A restart also loses custody (train state is in memory), exactly the strand task 4737 was filed for. — `orchestrator/src/orchestrator/merge_lane/types.py::InFlightMergeRegistry`
- **(b) in-progress with a live workflow or steward: parking and restoring races the workflow.** — The in-progress->merge-deferred edge is legal, but a live workflow keeps writing its own statuses (WORKFLOW_PRESERVE only governs terminal-decision reads), and merge-deferred -> in-progress is not an edge, so restore must be via pending, which makes it dispatchable while the original workflow or its claimant is still alive. The redrive guard only protects members that moved past merge-deferred. — `orchestrator/src/orchestrator/harness.py::build_train_callback_factory`
- **(b) Crash between CAS advance and the done flip leaves a landed-but-not-credited task if the origin status is restored first.** — reconcile_landed_row treats deferred/blocked/merge-deferred (WORKFLOW_PRESERVE) as 'already_done_pruned': it consumes the LandedRow without a done-write. Restoring blocked or deferred before the flip would hand that task to this prune path; leaving it at merge-deferred is also pruned, so credit then depends on the abandoned sweep's found_on_main re-drive. — `orchestrator/src/orchestrator/merge_lane/worker.py::reconcile_landed_row`
- **(b) Lane-owned done flip collides with the submitter's own stamp and with the delivered-checks gate.** — MCP submitters currently stamp done themselves; a lane flip makes that a duplicate done write, and for tasks carrying metadata.delivered_checks the lane flip is withheld and reverted to pending (a status the MCP submitter never put the task in). mark_member_done also never closes escalations or removes holds the human placed. — `orchestrator/src/orchestrator/harness.py::build_train_callback_factory`
- **Hand-carry worktrees can disappear at the next orchestrator restart while a lane-owned park is in progress.** — Harness._recover_crashed_tasks cleans a task-id-named worktree under worktree_base with no plan.json and no adoptable session, without consulting task status. A restore or re-drive that depends on that worktree would find it gone. — `orchestrator/src/orchestrator/harness.py::Harness._recover_crashed_tasks`

## OPEN QUESTIONS
- Should the coalesce path require a task status of merge-deferred at all for MCP singles? Table A already allows pending, deferred, in-progress and blocked -> done, so a design that skips the park and relaxes pre-check (a) needs no new Table A edge for the done flip, but still has no safe un-do for a non-landing train (re-pending clobbers the hold).
- If a park is wanted, is a new holding status or a metadata marker (for example metadata.merge_hold with the origin status) preferable to widening Table A with pending/blocked/deferred -> merge-deferred and merge-deferred -> deferred/in-progress, given deferral is write-authority protected and the sweep/recovery writers all assume pending?
- Where would the origin status and deferral record be stored so a lane or server restore survives an orchestrator restart (train state is memory-only today), and who restores after a crash while the member is parked?
- After absorption, who owns re-submission of an MCP single when its train derails? The caller was told 'superseded' and the lane keeps only a retired item. Does the design add a lane-side re-enqueue of the original MergeRequest, or require the caller to resubmit?
- How do MCP singles whose task_id differs from the branch, or that have no task row, behave as train members, given member ids are task_id values and stacking resolves branch_prefix + task_id?
- Does the lane or the submitter stamp done for an MCP single that lands in a train? The skills currently say the automatic flip exists only for coalesce-absorbed members and forbid self-stamping on that arm; what about the delivered-checks withhold and the open L1/L2 escalation on a blocked task the lane flips to done?
- Is the production orchestrator config the same as the repo's fused-memory/config/config.yaml (enforce_transitions true)? I read only the repo copy.
- Is the deferral lapse sweep (task 6526) landed in the running fleet? Docs say not; I found no src consumer, so held_by_session holds currently never lapse.
- Should the stranded reconcile and blocked redispatch sweeps learn 'a live MCP merge request or train custody holds this task' (InFlightMergeRegistry / train_member_ids_in_custody) rather than rely on claimants and pins?
