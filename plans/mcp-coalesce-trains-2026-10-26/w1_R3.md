# R3

An MCP merge_request is a fire-and-forget submission whose "waiter" is a bare shielded future in the escalation server's in-memory _waiters dict. Nothing consumes that future unless the caller passed wait_secs>0, and nothing on the lane side ties its outcome to the task. The escalation server is not a separate process: Harness._start_escalation_server runs it as an asyncio task on the orchestrator's own loop, sharing the same InFlightMergeRegistry, merge queue and worker, so it dies with the orchestrator and cannot outlive it. The submitter's own session is separate and only polls. MCP singles are built without awaited_by_workflow, so the coalescing pass excludes them. If they were admitted, the train's absorb step would resolve their future to MergeOutcome('superseded', superseded_by='coalesce-<tip>-<hex>'). The train id is not pollable, and merge_cancel refuses trains. The existing skills already document this superseded-by-coalesce-train path, because workflow singles take it today. They tell the submitter to poll the branch handle and run the ancestry check, and to never self-stamp done while the scheduler status is not done. That is the "landed-but-not-credited veto". The blocking mismatch is task status. The train's pre-check (worker.py::_do_train_merge step (a)) requires every member to be 'merge-deferred', and the only legal transition into that status is in-progress -> merge-deferred (shared/src/shared/task_transitions.py). Every MCP submitter class leaves its task at blocked (release_workflow park, stranded reaper), deferred (held_by_session or carried_by hold, planning carriers), in-progress, or has no task at all. The one exception is a hand-carry carrier deliberately walked to merge-deferred (OPERATIONS.md says this is supported and protected from the abandoned-member sweep while its request is live). Only non-task slug branches would pass the status gate today, via status_check's synthesised 'merge-deferred', and for them mark_member_done is a no-op. Credit (done + provenance) is stamped by the submitter by hand today (kind merged, or found_on_main with commit+note). The exceptions are the stranded reaper's blocked tasks, which the stranded-reconcile sweep credits as found_on_main when the branch is on main, and train members, which mark_member_done credits as kind='merged' with note 'train <id>'. The server persists only the escalation queue files; the merge journal (queue_store.py) and event store (sqlite) are the lane's durable state. The journal does not store awaited_by_workflow, so a recovered request is waiterless and flag-less. Any design that wants MCP singles in trains must decide who parks the task at merge-deferred, who credits done afterwards, and who tells the polling submitter that a superseded request has landed.

## 1. Server contract: merge_request
- [read] merge_request(task_id, branch, worktree, description='', wait_secs=0, verified_green=False, retry_failed_only=False, lane=None). branch and task_id are independent parameters. wait_secs is clamped to _MAX_WAIT_SECS (100); the wait is asyncio.wait_for(asyncio.shield(future)), and a timeout returns a non-terminal 'queued' shape without cancelling the request.  — `escalation/src/escalation/server.py::merge_request`
- [read] Response shapes: (a) fast-path already_merged with commit, no request_id (is_ancestor, or patch-id backstop, gated by the degeneracy guard); (b) 'queued' or 'attached' non-terminal shape {status, request_id, snapshot_tip, generation, position, queue_depth, eta_seconds, lane, lane_source, lane_applied}; 'attached' adds inflight_task_id, source, inflight_request_id, poll_by (request_id|task_id|branch) and pollable; (c) error shapes: duplicate_in_verify, invalid_lane, 'Merge queue not available'; (d) terminal {status, request_id, reason, conflict_details, push_status, commit, failure_diagnostic?, superseded_by?} where status is MergeOutcome.status verbatim.  — `escalation/src/escalation/server.py::merge_request; shared/src/shared/merge_state.py::MergeSubmitStatus`
- [read] The server builds the MergeRequest without awaited_by_workflow (default False) and without pre_rebased or task_files. It registers a WaiterRecord(source='mcp') in the in-memory _waiters dict, and a done-callback pops it. Dispatch goes through coalesce_or_enqueue_merge_request, which acquires the registry slot with source='mcp' (acquire's default).  — `escalation/src/escalation/server.py::merge_request; orchestrator/src/orchestrator/merge_lane/worker.py::coalesce_or_enqueue_merge_request`
- [read] When a train absorbs a single, the lane calls set_result(MergeOutcome('superseded', superseded_by=train_id)) on the single's future and retires its request_id. A merge_request(wait_secs>0) caller therefore gets status='superseded' with superseded_by='coalesce-<tipid>-<hex>' (the mr-* form is the generation-advance path). A caller who did not wait only sees it via merge_status.  — `orchestrator/src/orchestrator/merge_lane/worker.py::SpeculativeMergeWorker._stack_coalesce_train; escalation/src/escalation/server.py::merge_request`
- [read] The train id is not pollable as an outcome. merge_status(request_id=<train_id>) resolves via _durable_history's superseded_by lookup to state=stale_record with reason coalesce_train_id (an epistemic answer, not an outcome). The merge-queue skill says the same: it resolves through no tier, and the submitter must fall back to the branch handle plus an ancestry check.  — `escalation/src/escalation/server.py::_durable_history; shared/src/shared/merge_state.py::MergeReason.coalesce_train_id; skills/merge-queue/SKILL.md (Follow the superseded successor)`
- [read] A member's own record is frozen at 'superseded'. The event row recorded for the absorbed request carries state='superseded' and superseded_by; _current_run_answer returns it via map_terminal_state. It never turns into done even after the train lands. Polling the member by task_id or branch returns the same superseded record.  — `escalation/src/escalation/server.py::_current_run_answer; orchestrator/src/orchestrator/merge_lane/worker.py::enqueue_merge_request (_on_finalized)`
- [read] merge_status(request_id|branch|task_id) walks tiers: live worker snapshot -> event store (this run) -> git authority (probe_landing; needs branch or task_id) -> durable journal -> event store (prior runs) -> no_record. State vocabulary: live = queued, verifying, gate, finalizing (_map_live_state maps merging/awaiting_verify/verifying -> verifying, gate_reverify -> gate, finalizing -> finalizing); terminal = done, conflict, blocked, abandoned, superseded; epistemic = no_record, stale_record, journaled, unknown. 'finalizing' is a LIVE state, meaning the CAS advance of main is in progress.  — `escalation/src/escalation/server.py::merge_status, ::_map_live_state, ::_resolve; shared/src/shared/merge_state.py::MergeState`
- [read] merge_cancel(request_id) branches. (1) No waiter in _waiters (coalesced id, restart, a workflow-enqueued or recovered request): resolve via merge_status. If live, call _cancel_in_lane -> worker.cancel_request, then retire the entry. If the answer is terminal or epistemic, return cancelled=False. (2) Waiter whose future is already cancelled: 'abandoned', cancelled=False. (3) Waiter whose future is done: coarse terminal state, cancelled=False. (4) Waiter pending: cancel the future, then retire (release the slot, reap the worktree, clear retention) and return abandoned.  — `escalation/src/escalation/server.py::merge_cancel, ::_cancel_in_lane`
- [read] merge_cancel treats workflow-awaited requests differently only in the waiterless path. workflow_awaits = verdict.awaited_by_workflow OR registry.has_workflow_waiter(branch, request_id). If nobody awaits it, the server files a blocking L1 'merge_cancelled_by_operator' via _escalate_workflowless_cancel, the escalation a TaskWorkflow would have filed. The pending-MCP-waiter path 4 files no escalation. The detail text explicitly lists 'an MCP merge_request whose submitter is gone' as a workflow-less case.  — `escalation/src/escalation/server.py::_cancel_in_lane, ::_escalate_workflowless_cancel`
- [read] The lane refuses cancel for any GroupMergeRequest, and for a single in self._coalescing_ids (one the coalesce pass is stacking right now): refusal 'train_cancel_unsupported'. A cancel in the finalize window gets 'finalize_window'. Task 7309 is named as the work that replaces _train_cancel_refusal. Consequently an MCP single absorbed into a train cannot be cancelled by anyone.  — `orchestrator/src/orchestrator/merge_lane/worker.py::_train_cancel_refusal, ::SpeculativeMergeWorker.cancel_request`
- [read] MergeRequest.awaited_by_workflow is documented as 'True when a TaskWorkflow awaits this request's result and parks the task at merge-deferred on a superseded outcome'. It is not journaled, and PersistedMergeRequest has no such field. It is read for coalescing (worker._coalesce_exclusion_reason) and by cancel_request (MergeCancelVerdict.awaited_by_workflow).  — `orchestrator/src/orchestrator/merge_lane/types.py::MergeRequest.awaited_by_workflow; orchestrator/src/orchestrator/merge_lane/queue_store.py::PersistedMergeRequest`

## 2. release_workflow and task status at submit
- [read] release_workflow(task_id, timeout_secs=30) soft-cancels the workflow slot, waits for it to clear, then parks the task 'in-progress' -> 'blocked' (also for an orphaned in-progress task with no slot). It reports {released, was_active, slot_cleared, parked}. It parks nothing if the status is not in-progress (pending, deferred, blocked, terminal) or if a live slot reappeared. 'blocked' is the reaper-immune hold, and the later set_task_status('done') is the normal blocked->done transition. The skills require this call before the merge. A pending task instead needs a manual deferral hold, and the skills say never to hand-set blocked.  — `escalation/src/escalation/server.py::release_workflow; skills/unblock/SKILL.md (blocked-task merge procedure, step 1); skills/unblock-low-risk/SKILL.md (Procedure step 1)`
- [read] The only legal status transition INTO merge-deferred is in-progress -> merge-deferred (workflow._enter_merge_deferred or _handle_superseded). No pending, blocked or deferred -> merge-deferred edge exists. Legal exits from merge-deferred are done, pending, blocked and cancelled.  — `shared/src/shared/task_transitions.py::_UNION`
- [read] The train pre-check requires every member task's status to be 'merge-deferred', else it returns MergeOutcome('blocked', reason='Train merge rejected: not all members are merge-deferred...'). harness.build_train_callback_factory.status_check synthesises 'merge-deferred' only for ids the scheduler does not know (non-task members such as 'MCP-submitted branches like cargo-run-prebuilt-fix'), and only when the scheduler lookup succeeded. mark_member_done and redrive_member no-op for such ids.  — `orchestrator/src/orchestrator/merge_lane/worker.py::_do_train_merge (step a); orchestrator/src/orchestrator/harness.py::build_train_callback_factory`
- [read] On train landing, mark_member_done stamps mark_done(mid, kind='merged', sha, note='train <id>') for task members, after the delivered_checks guard. If the guard withholds, the member is reverted to 'pending'. redrive_member handles non-landed members (found_on_main -> done, else -> pending, skipping members no longer merge-deferred). Members whose status is not merge-deferred are left untouched.  — `orchestrator/src/orchestrator/harness.py::build_train_callback_factory (mark_member_done, redrive_member, _revert_withheld_member); orchestrator/src/orchestrator/merge_lane/member_redrive.py::MemberRedriver.redrive`

## 2. Submitter inventory
- [read] /unblock (blocked or escalated task): calls release_workflow first, so the task sits at 'blocked'. A task found 'pending' is held as 'deferred' with deferral held_by_session (never hand-set blocked). Submits merge_request(wait_secs=100, verified_green per rule), polls merge_status. On landing it stamps set_task_status(done, done_provenance={'kind':'merged','commit':sha}) or {'kind':'found_on_main','commit','note'}. On superseded it never resubmits or direct-merges, follows superseded_by, and uses the branch handle plus the ancestry check.  — `skills/unblock/SKILL.md (blocked-task merge procedure steps 1, 7, 8; Polled terminal failures superseded bullet; resumed poll)`
- [read] /unblock on a coalesce-* absorption: the two exits are (1) landed AND scheduler status already 'done' -> skip the stamp, go to cleanup; (2) any other status -> take the landed-but-not-credited exit and never stamp. Its landing signals are the tip's merge marker ('Merge task/<TIP_ID> into main' selected by exact subject) and the task's own scheduler status. rc=1 on the member's own ancestry check is the permanent normal state for a non-tip member.  — `skills/unblock/SKILL.md (resumed poll); skills/merge-queue/SKILL.md (Follow the superseded successor rules 1-4, 2v)`
- [read] /unblock-low-risk (autonomous, launched as a sub-agent by the L2 escalation-watcher): release_workflow, requires parked='blocked' or an already-blocked task, then merge_request, polls, and on done stamps done_provenance merged or found_on_main, restores metadata via update_task(append=true), and calls resolve_issue. On superseded: no merge_cancel (a no-op on an absorbed id, and trains cannot be cancelled), resolves by ancestry. Two exits are success (stampable sha; landed and already credited -> skip the stamp, cleanup, resolve). The third, if unresolved, is to keep polling the branch handle or ABORT with a non-failure 'in flight on successor' disposition and leave the escalation pending. If the merge is live at the polling deadline it returns outcome 'handed_off' and never cancels.  — `skills/unblock-low-risk/SKILL.md (Procedure steps 1, 8, 9; superseded bullet; resume mode); skills/escalation-watcher/SKILL.md (handed_off completion handling)`
- [read] /merge-queue skill (any session landing a task branch, including hand carries): submit merge_request(wait_secs=100), poll merge_status (15->60 s backoff, eta_seconds hint), cleanup, then step 4 stamps set_task_status(done, done_provenance={'kind':'merged','commit':<sha>}). The sha comes from the submit response's 'commit', or from the marker/ladder derivation when polled, as found_on_main for already-on-main landings. It says explicitly 'do NOT fall back to direct merge or resubmit on superseded', and merge_cancel is the only abandon path (best-effort when poll_by is task_id or branch).  — `skills/merge-queue/SKILL.md (steps 3, 4, 5, superseded sections)`
- [read] Hand carry / carrier tasks: the carried task is held as 'deferred' (held_by_session, then carried_by(<carrier>)) so the scheduler won't dispatch it. A planning-mode carrier is deferred. OPERATIONS.md also describes a carrier 'walked to merge-deferred and submitted with merge_request': it is held (the abandoned-member sweep ignores it) for as long as its request is live, and a 'superseded into a train that derailed' outcome starts the two-pass abandonment count. The done stamp is by hand through set_task_status(done) (deferred->done and blocked->done are legal), with the provenance kinds above.  — `OPERATIONS.md ('Holding a member during a hand-carry'); docs/task-authoring.md (Deferring a task: Hand-carry); skills/unblock/SKILL.md (step 1 deferral hold)`
- [read] escalation-watcher actions: the L2 watcher does not call merge_request itself for B3. ## 3. The landed-but-not-credited veto
- [read] Quote (rule 2v of the Follow-the-superseded-successor section): 'Once it has, the work landed — but there is no self-stamp on either arm: signal (b) is a veto, not a corroborator... Any other status — pending, merge-deferred, anything else, including a status you cannot read — means do not write, ever'. Exit: 'keep polling... If a non-done status still holds at rule 3's existing 20-minute wall-clock ceiling, stop and report to the human — report it as landed-but-not-credited, citing the tip merge sha and the current status..., never as not landed — and never resubmit, never direct-merge, never self-stamp.' It applies to the coalesce-* arm (rc=128-with-empty-marker and rc=1). Signal (a) is the tip's merge marker on main, found by an exact-subject search; signal (b) is the member's scheduler status, which must have been flipped to done by mark_member_done.  — `skills/merge-queue/SKILL.md (rule 2v, 2a, 2b); skills/unblock/SKILL.md (resumed poll); skills/unblock-low-risk/SKILL.md (superseded bullet)`
- [read] Why the veto exists: a non-done status after a train landing means one of three things. (1) pending: _revert_withheld_member reverted the member because the delivered_checks guard could not verify the declared capability on main (the member's only recovery edge). (2) merge-deferred: the normal pre-merge park, or a FAILED revert flagged for operator attention. (3) done_wip_recovery: main advanced but members were not flipped (split-brain, escalated). Stamping done over any of these overrides a deliberate orchestrator decision: it destroys the recovery edge, marks done a task whose capability isn't on main (unblocking its dependents via the delivered-check gate), and races a scheduler re-dispatch. A git cherry content proof cannot discharge it. The veto assumes the credit comes from the orchestrator's mark_member_done, which requires merge-deferred status in advance.  — `skills/merge-queue/SKILL.md (rule 2v bullets); orchestrator/src/orchestrator/harness.py::build_train_callback_factory (_delivered_checks_withhold, _revert_withheld_member)`
- [inferred] Consequence for an MCP single absorbed into a train under today's code: its task is blocked/deferred/in-progress, not merge-deferred, and the mark_member_done path (the only credit the veto accepts) would not apply to a status that never reached merge-deferred. The veto would stop the submitter from stamping done, so the task would stay uncredited (landed-but-not-credited) until a human acts, or until the stranded-reconcile sweep marks a blocked task found_on_main. For a non-tip member that sweep does not fire: its ref is stale-by-rebase, so the branch state is not ON_MAIN or GONE_WITH_MERGE_MARKER.  — `skills/merge-queue/SKILL.md; orchestrator/src/orchestrator/harness.py::Harness._reconcile_one_stranded; orchestrator/src/orchestrator/task_ground_truth.py::ON_MAIN_BRANCH_KINDS`

## 4. Who could own a waiter: process, lifetime, persisted state
- [read] The escalation MCP server is hosted inside the orchestrator process: Harness._start_escalation_server calls create_server(..., merge_queue=self._merge_queue, harness=self, merge_inflight_registry=self._merge_inflight_registry) and runs uvicorn as asyncio task 'escalation-server' on the same loop (optionally on a systemd-held socket, so the listening socket, not the state, survives restarts). It shares the live registry, worker snapshot and scheduler with the lane. It cannot outlive the orchestrator, and the submitter's Claude session has no bearing on it.  — `orchestrator/src/orchestrator/harness.py::Harness._start_escalation_server; escalation/src/escalation/server.py::create_server`
- [read] The submitting session does not own the request. Cancelling the merge_request tool coroutine (MCP disconnect) does not cancel the future (shield), and merge_cancel is the only explicit cancel. The request therefore outlives the submitter session and keeps no per-session state. Only the lane (worker) and the server's in-process dicts hold it.  — `escalation/src/escalation/server.py::merge_request; skills/merge-queue/SKILL.md (merge_cancel: 'durable intent')`
- [read] Persisted vs in-memory state. Server _waiters dict and InFlightMergeRegistry: in-memory only, lost on restart. Merge journal (merge_queue.json via MergeQueueStore): the request identity fields, lane and enqueued_at; no flags, no waiters, no train. LandedOutbox: durable landed rows keyed by task_id, fsynced write-ahead, consumed on confirmed done. Event store (sqlite): merge_queued, merge_coalesced, merge_finalized (state, superseded_by, absorbed_request_ids), train events. Escalation queue directory (file-based). Task store: the fused-memory Taskmaster, reached through harness.scheduler. A train-coalescing gate that needs an 'owner' for an MCP request has these places to put it: a flag on MergeRequest (journaled or reconstructed), a new waiter source on the registry (WaiterRecord.source already distinguishes 'mcp', 'workflow' and 'recovery'), or the server's _waiters.  — `orchestrator/src/orchestrator/merge_lane/types.py::InFlightMergeRegistry, ::WaiterRecord; orchestrator/src/orchestrator/merge_lane/queue_store.py; orchestrator/src/orchestrator/merge_lane/landed_outbox.py; escalation/src/escalation/server.py::merge_request`
- [read] A waiter exists on the lane side already for workflow singles: register_and_enqueue_merge_request acquires the registry slot with the workflow's future; the registry tracks WaiterRecord.source and has_workflow_waiter(branch, request_id) is true while a workflow is attached to that entry. This is what the server's merge_cancel consults. The MCP path registers its waiter only in the server's _waiters and gives the registry a default source='mcp'.  — `orchestrator/src/orchestrator/merge_lane/types.py::InFlightMergeRegistry.has_workflow_waiter; orchestrator/src/orchestrator/merge_lane/worker.py::register_and_enqueue_merge_request`

## HAZARDS
- **/unblock, /unblock-low-risk and /merge-queue singles (task blocked via release_workflow): the train never lands, or lands without crediting.** — The task is 'blocked' (release_workflow parks in-progress -> blocked) and has no legal transition to merge-deferred. status_check reports 'blocked', so _do_train_merge returns 'Train merge rejected: not all members are merge-deferred' (the pre-4953 incident class). The rewritten tip branch and the stacked members' worktrees are left to be unwound (restore_pre_stack_tips and redrive). redrive_member skips members that are not merge-deferred, leaving the single un-driven. If the pre-check were bypassed, mark_member_done would credit a task nobody parked. — `orchestrator/src/orchestrator/merge_lane/worker.py::_do_train_merge; shared/src/shared/task_transitions.py::_UNION; escalation/src/escalation/server.py::release_workflow`
- **The same skills' submitter is left with an unpollable superseded and no done flip. It stops with 'landed-but-not-credited'.** — The absorbed request gets MergeOutcome('superseded', superseded_by='coalesce-...'). merge_status stays frozen at superseded, and the train id polls as stale_record/coalesce_train_id. The skills fall back to the branch handle plus the tip-marker ancestry check. For a non-tip member rc=1 is permanent. The veto forbids stamping unless the scheduler already reads done, and for a blocked or deferred task nothing flips it, so the loop hits its 20-minute ceiling and reports to a human. /unblock-low-risk would abort with an 'in flight on a successor' disposition and leave the escalation pending. The task also stays blocked, where the stranded-blocked redispatch may re-pend it (if no pinning escalation or claimant holds it). — `skills/merge-queue/SKILL.md (rules 1-4, 2v); skills/unblock-low-risk/SKILL.md (superseded bullet); escalation/src/escalation/server.py::_durable_history`
- **Deferred hand-carry tasks (held_by_session or carried_by hold), and planning-mode carriers submitted while deferred.** — The task is 'deferred' and cannot be moved to merge-deferred (Table A allows only in-progress -> merge-deferred). status_check fails, as above. The deferral sweep and carried_by hold semantics assume a human or the carrier closes deferred -> done by hand. A train absorbing the carrier would leave the task deferred with the work on main, and the veto says do not stamp. The carried task's hold may also expire (dead session -> released to pending after grace), letting the scheduler re-dispatch work that already landed. — `docs/task-authoring.md (Deferring a task: lease rule, Hand-carry); shared/src/shared/task_transitions.py::_UNION; skills/merge-queue/SKILL.md`
- **A hand-carry carrier walked to merge-deferred is the one class that passes the status gate today.** — OPERATIONS.md says such a carrier is protected from the abandoned-member sweep while its merge_request is live. If absorbed into a train it would be credited by mark_member_done (kind='merged', note 'train <id>'), so it is correct, but the carrier has no workflow parked, no MemberRedriver custody beyond the lane's, and the abandoned-member sweep's 'live request' owner check (requests.task_ids_in_flight) ends the moment its request resolves as superseded, so the two-pass abandonment count could start while the train is still verifying. - **Stranded-branch reaper: the dedup marker, the done-callback and the credit path all misfire.** — The reaper calls enqueue_merge_request directly (no registry slot) and leaves the task 'blocked'; absorption resolves its future 'superseded', which _on_stranded_merge_done treats as a strict no-op, and the metadata.stranded_merge_request marker says 'presumed in flight' for the grace window then permits a re-submit of the same branch. status_check would reject the blocked task anyway.
