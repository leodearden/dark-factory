## 1. Goal (G1 consumer + user-observable surface)

When an attended quality run ends, the project's task tree holds a visible chain that, without anyone remembering, asks Leo for the next run once enough of this run's work has landed — and never asks early, never asks daily, and never runs the skill itself. Observable:

- A completion gate that is not yet satisfied stays `pending` with `metadata.milestone.at` advanced by `before_done.recheck_secs`, a `predicate_rearmed` row in the orchestrator event store, and **no escalation**. A gate that stays unsatisfied for `deterministic.predicate_recheck_stall_cap` consecutive checks files one born-at-L2 `milestone_check_stalled`. Consumers: the completion gates the skills file (`skills/_shared/filing-the-trigger-chain.md`), any future predicate that wants "not yet".
- `scripts/check_run_completion.py --run <run_id> --threshold 0.7 --project-root <root>` exits `0` / `75` / `2` and ends its output with a one-line JSON verdict; `weighted_completion` and `run_tasks` are importable. Consumers: the completion gate (filed per the snippet), the census trigger's completion condition (`plans/census-incremental-prd.md` L8b, which calls the CLI), the `--pending` report (ε).
- When the completion gate passes, the human gate files a born-at-L2 `review_due` escalation carrying a typed `review_due` payload (skill, project, run id, the gate's verdict). The escalation watcher spawns an attended `/<skill>` session directly when Leo is present and puts the item in the digest when he is not. Consumer: Leo, through `skills/escalation-watcher/SKILL.md`.
- `scripts/check_run_completion.py --pending` lists every open chain per project with its live share. Consumer: Leo (CLI), and the watcher's `review_due` brief line.
- `skills/_shared/filing-the-trigger-chain.md` (landed with the contract) gives the exact `submit_task` shapes; this PRD's code must accept them as written (λ row 14). Consumers: `skills/review/`, `skills/hotspot-survey/`, `skills/review-all/`.

## 3. Sketch of approach

α lets a predicate name a script in the dark-factory tooling checkout, so one script serves every project. β adds the third predicate verdict: exit `75` (`os.EX_TEMPFAIL`) re-arms a dated gate by `recheck_secs`, records the verdict, and escalates only after a configurable streak. γ types the chain (`metadata.trigger_chain`), validates its two carriers, and refuses a second open chain per (project, skill). δ is the measure and the predicate. ε is the `--pending` report. ζ makes the human gate's L2 discriminable (`review_due`) and structured. η teaches the watcher to route it. θ updates `docs/task-authoring.md`. ## 4. Contracts (H)

### C1 — the predicate exit-code contract gains a re-arm verdict (amends `docs/task-authoring.md` §6)

> **Exit `75` from a predicate that declares `before_done.recheck_secs` means "not yet": the task returns to `pending` with its dated milestone advanced, stamps nothing terminal and files nothing — until the streak cap, which files one escalation.**

- **Shape.** `BeforeDone.recheck_secs: int | None` — strict int, `>= 300`. Present only when `kind='predicate'` **and** `metadata.milestone.mode == 'dated'`; forbidden on `kind='deploy'` and with a `delayed` or absent milestone. The kind half lives on `BeforeDone`; the milestone half lives on `TaskMetadata`'s cross-field validator. That puts it at the write boundary under `enforce=True`, covering `update_task` too. The submit guard **delegates** to both, as `_validate_milestone` delegates to `Milestone` — one home per rule (heuristic 10 *uniformly*, heuristic 11).
- **`delayed` is forbidden**, not defined. The re-arm rewrites `at`, which a `delayed` milestone must not carry (§6 iff). Its anchor is frozen-once by design, and rewriting it would break that promise. The completion gate is therefore `dated`, first firing one interval after the run.
- **Verdict table** (runner, `_run_predicate`):

| exit | condition | outcome |
|---|---|---|
| `0` | — | unchanged (`done`, `deterministic-milestone`), plus stamps `predicate_verdict` |
| `75` | `recheck_secs` set, milestone `dated`, streak `< cap` | **re-arm** (below); returns `WorkflowOutcome.REQUEUED` |
| `75` | streak reaches `cap` | born-at-L2 `milestone_check_stalled`, stamp `gate_escalated_at`, reset streak to 0, `blocked` |
| `75` | no `recheck_secs`, or milestone not `dated` (a post-submit edit, task 3093) | today's `milestone_check_failed`, plus one detail line naming the missing declaration — never a silent re-arm (INV-11) |
| other non-`0` | — | unchanged (`milestone_check_failed`), plus stamps `predicate_verdict`, resets streak |
| no verdict | — | unchanged (§6 last row) |

- **Re-arm.** One `update_task(metadata_mode='merge')` writes three keys. `milestone` is rewritten as the whole dict, since merge is shallow: `{**milestone, 'at': next}` with `next = now + recheck_secs`, UTC ISO. `predicate_recheck` = `{consecutive, first_rearmed_at, last_checked_at, next_check_at}`. `predicate_verdict` is the third. Then a best-effort `set_task_status('pending')`, the same trailing-write pattern as `_file_milestone_check_failed_and_block`. The metadata write comes **first**, so a lost status write leaves an in-progress task whose `at` already withholds re-dispatch; the existing stranded-in-progress reconcile reverts it (λ row 9).
- **`predicate_verdict`** is the trailing **JSON-object** tier of `orchestrator/src/orchestrator/deterministic_runner.py::_extract_predicate_payload`, parsed and stored as a dict. The clean-line tier is never stored. A payload over 400 chars is stored as `{"elided": true, "chars": N}`. `_extract_predicate_payload` is refactored so the string rendering derives from the parsed object — one parser (heuristic 11). Stamped on every verdict-bearing exit (0, 75, other), uniformly.
- **Observability (INV-2).** Re-arm logs at INFO `task <id> predicate re-armed (rc=75, consecutive=<n>/<cap>, next_check_at=<iso>): <verdict>` and emits `EventType.predicate_rearmed`. A stall emits `EventType.predicate_recheck_stalled`. Both go through `scheduler.event_store` (None-tolerant) with `data={rc, consecutive, stall_cap, recheck_secs, next_check_at, verdict}`. The finding run id, share and threshold travel inside `verdict`, because the runner parses no output for its decision (§6) and so cannot name script-defined fields itself. The event row's own `run_id` column is the orchestrator run.
- **Stall escalation.** Category `milestone_check_stalled`, `severity='critical'`, `agent_role='orchestrator-deterministic'`, `level=2`. Detail: the streak, cap, `first_rearmed_at`, `recheck_secs`, the last verdict, and the three resolutions. `resume` keeps waiting with the streak restarted (resume re-runs the predicate, verified at `orchestrator/src/orchestrator/deterministic_runner.py::DeterministicRunner.run` §1). `abandon` on the **completion gate** fires the human gate now, because a cancelled dependency satisfies. `abandon` on the **human gate first**, then the completion gate, ends the chain. The category joins `escalation/src/escalation/authority.py::L2_AUTO_CLOSE_DENY_CATEGORIES` and `escalation/src/escalation/shadow_ruling.py::_MILESTONE_CATEGORIES`. INV-4: the cap is the storm escape of the re-arm loop. INV-7: the hold's owner is the task's own `trigger_chain`/`predicate_recheck` record, bounded by the cap.
- **Config.** `OrchestratorConfig.deterministic.predicate_recheck_stall_cap: int = 30` (`ge=1`). It is registered in `orchestrator/src/orchestrator/config.py::RELOADABLE_FIELDS` (green tier) and read when `orchestrator/src/orchestrator/harness.py::Harness._run_deterministic_slot` constructs the runner per slot, so it is live on reload. The default of 30 (30 daily checks = 30 days) is decided (§13). Calibrate from `predicate_recheck_stalled` events after the first quarter.
- **Interactions.** *Recurrence:* `75` is non-terminal, so the mint (C-2 of the recurring PRD, task 4677) never fires. A carrier re-arms in place, and its gauge (task 4679) reads `scheduled`. *Crash-resume:* the check is read-only; a re-run before the metadata write repeats a harmless read, and the streak counts writes, not runs. *`gate_escalated_at`:* a re-arm after a resolved escalation leaves the stamp. §1 of `run()` then routes the next dispatch through the predicate-resume branch, which re-runs the check — identical behaviour (λ row 8). *Retry cap:* a deterministic slot returns before `report` is bound in `orchestrator/src/orchestrator/harness.py::Harness._run_slot`'s finally, so `REQUEUED` never reaches `Harness._apply_retry_cap` (verified: the finally's "report is None, e.g. the deterministic-gate early return" path).
- **Byte-identity.** Every existing predicate lacks `recheck_secs`, so its behaviour is unchanged except the additive `predicate_verdict` stamp and, on `rc=75`, one extra detail line.

### C2 — `metadata.trigger_chain` (Tier-A, typed)

```
trigger_chain = {
  role:          "completion_gate" | "human_gate",
  skill:         "review" | "hotspot-survey" | "review-all",   # BARE name, no slash; closed Literal; a new attended instrument extends it here
  run_id:        "<contract §5 run_id>",                       # must start with f"{skill}-"; validated, never routed on
  superseded_by: "<run_id>" | null                             # written by a superseding run (C5); default null
}
```

- **Skill spelling** (contract §11, snippet §0): `skill` is the bare skill name, never `/review`. The Literal itself rejects any other value. A leading `/` gets a dedicated message, `trigger_chain.skill='/review' must be the bare skill name 'review' (no leading slash)`, so the error names the fix (heuristic 10 *informatively*). The model raises it, and the submit guard surfaces it as a `ValidationError` with the same hint.
- **Shape:** `shared/src/shared/task_metadata.py::TriggerChain`, registered through `register_metadata_submodel` (cardinality `dict`) and added to `_BLESSED_METADATA_KEYS`. Runner-stamped `predicate_recheck` and `predicate_verdict` are blessed beside it.
- **Carrier rules** (submit guard `_validate_trigger_chain`, mirroring `_validate_recurrence`):
  - `completion_gate` ⇒ `task_kind='deterministic'` ∧ `before_done.kind='predicate'` ∧ `before_done.recheck_secs` ∧ milestone `dated`.
  - `human_gate` ⇒ `task_kind='deterministic'` ∧ `always_escalates is True` ∧ `before_done is None`; the milestone is optional (`delayed` in the interim form).
  - Either role ⇒ no `x_finding_run`, because a chain task must never count toward its own measure. This is enforced at submit only: the tool rows δ reads carry no metadata, so the measure cannot re-check it. λ row 1 pins the consequence, that the selection holds exactly the run's three tasks while its chain is open.
- **One open chain per (project, skill).** A new leaf module, `fused-memory/src/fused_memory/middleware/trigger_chain_guard.py` (function `trigger_chain_open_error`), is wired in `fused-memory/src/fused_memory/server/tools.py::submit_task` directly after `recurring_gate_guard_error`. It covers the curator and `planning_mode` paths alike. Its injected corpus read is the lookup PRD's in-process method, `TaskInterceptor.find_tasks_by_metadata(key='trigger_chain', value=None, statuses=ACTIVE)`. Each row's `matched_value` is the whole `trigger_chain` dict, so the guard needs no nested path. Unlike task 3588's guard it does not materialise the active corpus. It refuses a chain task when a non-terminal task in the project carries the same `skill`, a **different** `run_id`, and `superseded_by is None`. "Non-terminal" is `shared.task_statuses.ACTIVE`, which includes `deferred`, so an uncommitted interim gate counts as open — matching the snippet's §1. The error is structured: `error_type='TriggerChainOpen'` and `open_chain=[{id, role, status, run_id}]`, with a hint naming C5. It applies to every caller, not only recon. It fails **open** with a WARNING on a read error, as task 3588's guard does: the cost of failing open is one duplicate chain, bounded by the run rate.
- **Capability report and version skew.** The snippet's first probe (an executable script in the factory root) proves the code is on main. It does not prove the **running** fused-memory guard has it. Two mechanisms close that gap:
  - `shared/src/shared/task_metadata.py` gains `TASK_METADATA_CAPABILITIES = frozenset({'before_done.recheck_secs', 'before_done.script_root', 'trigger_chain'})`, the one home. `fused-memory/src/fused_memory/server/tools.py::get_status` returns it as a top-level sorted list, `task_metadata_capabilities`, beside `reconciliation_halt`. Because the list comes from the running process, it is the second half of the snippet's §2 probe.
  - The submit guard closes `before_done`'s key set to `BeforeDone`'s declared fields. An unknown key is refused with `error_type='UnsupportedTaskMetadata'`, naming the key and the running capabilities. The snippet falls back to the interim form on that `error_type`. This is safe for existing writers: on 2026-10-04 every stored `before_done` in the dark_factory (66) and reify (5) stores uses only the seven declared keys.
  - A pre-γ server reports no list and does not refuse. On dark_factory it would silently accept `script_root`/`recheck_secs`, which is why the probe, not the rejection, is the primary check.
- **Residual (named):** the carrier rules are submit-time only (task 3093, the same residual §6.1 states for `recurrence`). The `recheck_secs` milestone rule is not, because it lives on `TaskMetadata` (C1).

### C3 — the weighted completion measure (`scripts/check_run_completion.py`)

- **Importable API** (one home; no re-export shim, heuristic 13):
  - `PRIORITY_WEIGHTS = {critical: 4, high: 3, medium: 2, low: 1, polish: 1}`. All five weights, and missing = `medium`, are contract §11's.
  - `weighted_completion(tasks: Iterable[Mapping[str, object]], threshold: float) -> CompletionVerdict`. A pure function over each task's `status` and `priority`; it does no I/O and applies no selection.
  - `run_tasks(project_root: str, run_id: str, *, call_tool=<HTTP binding>) -> list[dict]` — the selection. It calls `find_tasks_by_metadata(project_root, key='x_finding_run', value=run_id, limit=100)`, pages on `pagination.has_more`, and returns the rows (`task_id, status, priority, …`). The tool is owned by `plans/task-metadata-lookup-prd.md` L1. `call_tool` defaults to `scripts/legibility/census_trigger.py::post_mcp_tool_call` bound to `FUSED_MEMORY_MCP_URL` (default `http://localhost:8002`), the transport that PRD names. Tests inject a binding.
  - `CompletionVerdict` — a frozen dataclass (heuristic 8): `run_id, threshold, share: float | None, landed, pending, total, vacuous, passed, by_priority`, plus `to_json() -> str`.
- **Arithmetic** is exactly contract §11. A NULL priority weighs as `medium` (contract §11; also the store's own read default, so the measure and every reader of the store agree). A priority outside the five tiers raises `UnknownPriority(task_id, value)`, which the CLI reports as exit 2: validate, never coerce, the precedent of `scripts/legibility/census_trigger.py::compute_tasks_landed`. `passed` compares `Fraction(landed, landed + pending) >= Fraction(str(threshold))`, so 7/10 against 0.7 is exact (G6 exactness: a float `0.7*10` is `7.000000000000001`). `threshold` must satisfy `0 < t <= 1`.
- **Edge cases.** `total == 0` (no task carries the run id) → `share=None`, `passed=False`; the CLI exits **2** ("no tasks carry x_finding_run=<run>"), because a chain is only ever filed for a non-empty run (C5), so this means a wrong run id. All cancelled (`total > 0`, denominator 0) → `vacuous=True`, `share=None`, `passed=True`, exit 0: nothing is left to land, so the human gate should fire.
- **CLI.** `--run R --threshold T --project-root P`, all required in the check mode. `T` is a fraction in (0, 1]; the census converts its `completion_threshold_pct` itself. Exits: `0` pass; `75` (`os.EX_TEMPFAIL`, the one home for the number) not yet; `2` could-not-check. Exit 2 covers usage errors, a transport failure, a tool `error` payload, an empty population (`"error":"empty_run"`) and an unknown priority. A store failure is never read as "not yet": that is lookup decision 2. An uncaught crash surfaces as Python's `1` and escalates as a failed check. Human-readable lines come first; the **last line** is the compact JSON verdict, the only `note` tier with a guarantee (§6; heuristic 12):

```
{"run":"review-dark_factory-20261004","verdict":"not_yet","share":0.6286,"threshold":0.7,"landed":22,"pending":13,"total":17,"vacuous":false,"by_priority":{"high":[5,2,1],"medium":[3,2,0],"low":[1,3,0]}}
```

`verdict ∈ {pass, not_yet, error}`. `by_priority` maps each tier that has any task to `[done, open, cancelled]` counts. `error` verdicts add `"error": "<bounded reason>"`. A test pins the worst case (all five tiers, six-digit counts) at ≤ 400 chars, the `note` cap.
- **Environment.** Runs under the orchestrator's inherited `uv run` venv. The dark_factory orchestrator unit is `ExecStart=uv run --project orchestrator …`, and `DeterministicRunner._default_run_script` inherits `os.environ`, so `python3` is the venv interpreter with `httpx` and `yaml` available. `scripts/` is `sys.path[0]` for a direct run, so `legibility.census_trigger` imports. Mode `100755`, `#!/usr/bin/env python3`.

It is `None` in the interim form, and also when the read fails; the second case adds a detail line naming the error, never a silent omission.

The category is `review_due` iff `trigger_chain.role == 'human_gate'`, and `milestone_gate` otherwise. Callers fetch the completion gate (the dependency whose `trigger_chain.role == 'completion_gate'`) through `scheduler.get_task`.
- Resolve-to-done is unchanged: `resume` → `pending` → §1 → `done` (`deterministic-gate`). For a `human_gate` the provenance cites `escalation_id`, the newest own `review_due` record, so the closure is traceable (task 3181's lesson about generic notes).
- `ReviewDueState.skill` carries the same bare name, copied from the validated `trigger_chain.skill`; `ReviewDueState` is typed to the same Literal, and its builder rejects a slash-prefixed value rather than storing it. Rendering adds the slash: the summary is the task title, `Run /<skill> on <project_id> (<run_id> landed)` (contract §11). The builder renders `f"/{skill}"` for the title, the summary and η's spawn line, which keeps the slash out of stored data (heuristic 12).

### C5 — chain lifecycle

The calls are `skills/_shared/filing-the-trigger-chain.md`'s (the one copy); this section states the mechanism they rely on, with the snippet section each step corresponds to.

1. **File** (end of an attended run that filed ≥ 1 task). Order: check for an open chain (snippet §1) → supersede it if one exists (§5, step 5 below) → file this run's chain (§3 or §4) → commit. **Final form** (§3): completion gate plus a human gate depending on it. **Interim form** (§4, contract §11): one human gate, `milestone: {mode: delayed, after_secs: 259200}`, depending on the run's `high`/`critical` tasks, or on all of them when there are none of those. **Commit timing:** commit at once only when every task the run will file already exists. A program run, whose tasks later `/prd` sessions file, leaves its chain `deferred` until its FILED table is complete. In the final form this is because the measure covers only tasks already carrying `x_finding_run`, so an early commit could pass on the first tickets. In the interim form it is because a delayed milestone with no dependencies anchors at once. **Form probe** (§2, two parts, both required for the final form): (i) `scripts/check_run_completion.py` is executable in the dark-factory checkout, never the target project. δ depends on α, β and γ, so this proves the code is on **main**. (ii) The running fused-memory's `get_status` lists the three `task_metadata_capabilities` (C2 "Capability report"), which proves the **running** guard has the code. Either part missing → interim form. A final-form submit refused with `error_type='UnsupportedTaskMetadata'` also → interim form. The orchestrator side is covered by timing: the first check fires 24 h after commit, longer than the 8 h fleet-redeploy clock, and a pre-β runner that meets a `75` files `milestone_check_failed`, which is loud, never silent. A run that filed **no** tasks files no chain and says so in its report (contract §11).
2. **Wait**: a daily predicate; `75` re-arms; the streak cap files `milestone_check_stalled`.
3. **Fire**: the completion gate goes `done` → the human gate dispatches → `review_due` L2.
4. **Route** (η): attended → spawn directly, with no prior ask: `/spawn "/<skill> <project_root> --launched-from <esc id>"`, rendered from the `review_due` payload (C4), under the watcher's "Sub-agent or `/spawn`" rule (a multi-turn session). `review_due` is therefore an exception to the watcher's "Always ask" entry for deterministic-runner filings (D10). The skill confirms scope and cost with Leo before launching any agent, so nothing runs without him. AFK → digest plus DecisionRecord, **never** a spawn and never a sub-agent that runs the skill (ruling 2).
5. **Answer and supersede are one step** (snippet §5). The spawned run's §1 check finds the chain that launched it: its human gate is `blocked` on the launching `review_due`, and its completion gate is `done`. Supersede mechanism, in order:
   (a) Each old chain task gets `trigger_chain.superseded_by = <new run_id>` (the whole dict, because merge is shallow). This clears the C2 guard at once.
   (b) The old human gate goes first, always, because a cancelled completion gate satisfies its dependency and would fire it. If `blocked`, its pending escalation is resolved **once** with `resume`, which drives the gate to `done`. The resolution text is `ran as <run_id>` when that escalation is the one in `--launched-from` (the normal case), else `superseded by <run_id>`. If `pending` or `deferred`, it is cancelled.
   (c) The old completion gate (final form only) is cancelled if `pending`, resolved with `abandon` if `blocked`, and re-read if `in-progress`.
   Nothing resolves the launching escalation a second time, and no gate is re-filed: the old gate is terminal and the new chain belongs to the new run. A run started without a gate (e.g. `/review` run early) follows the same path with `superseded by`. Once γ lands, a skipped §1 check is caught too: the first submit is refused with `TriggerChainOpen`, and §5 applies.
6. **Decline**: "not now" → leave the L2 pending; it is quiescent, re-files nothing, and stays a standing brief item. "End the cadence" → `abandon` on the human gate; the next attended run starts a new chain.

## 5. Resolved design decisions

- **D1** The re-arm advances `milestone.at`; no second clock. The scheduler already re-reads `at` every tick (`orchestrator/src/orchestrator/scheduler.py::Scheduler._milestone_time_gated`), so the persisted value is the only timer and it survives restarts.
- **D2** `delayed` + `recheck_secs` is forbidden, not defined (C1).
- **D3** The completion gate is **not** a `recurrence` carrier: one gate re-arms in place until it passes; there is never a successor. "Recurring" in ruling 1 is read as "re-arming".
- **D4** The cap counts consecutive 75s and is config, not per task. Per-task recheck intervals make its wall time vary; the escalation detail states the elapsed time.
- **D5** The measure, its selection and the CLI share one file, `scripts/check_run_completion.py`, the path the census PRD cites. Ruling 3 is met two ways. The census calls the CLI (its L8b), which is its choice. `weighted_completion` is importable for any in-process caller, because `scripts/` is on `sys.path` both for the nightly units (`scripts/legibility/nightly.py` bootstrap) and for the tests (`scripts/tests/conftest.py`).
- **D6** Store reads go through the `find_tasks_by_metadata` MCP tool, not through read-only sqlite. This adopts `plans/task-metadata-lookup-prd.md` decision 2: one implementation at the store owner, no second-process open of the store, and the server resolves the per-project store path. That gives one query helper, not two. Owner: the lookup PRD; this PRD consumes it in δ and ε over MCP, and in γ in-process. A store or transport failure exits 2 and escalates. A fused-memory restart that coincides with a daily check therefore costs one `milestone_check_failed`, which `resume` clears by re-running. The forensic-sqlite alternative was rejected because it would turn `CLAUDE.md` §Forensic reads into an operating path, and because it would restate column names the store owns.
- **D7** Chain identity is a typed Tier-A key (`trigger_chain`), not Tier-C `x_trigger_for`: the runner routes on it (C4), and Tier-C keys are unvalidated annotations (`docs/task-authoring.md` §8 Tier-C). Chain tasks carry no `x_finding_run` (C2).
- **D8** Escalation routing keys on a category plus a typed payload (`review_due`), never on summary text (heuristic 12).
- **D9** The completion gate's threshold lives in its `before_done.args` (the write-triage D3 precedent). `--pending` reads it back with the script's own argparse parser, so the thresholds have one home and need no second parser.
- **D10** Spawn when attended, directly, without a prior ask (C5 step 4); the spawned session is the ask. Decided by Leo, 2026-10-05 (§13).
- **D11** `os.EX_TEMPFAIL` is the single home for the number 75. The runner and the script both import it.
