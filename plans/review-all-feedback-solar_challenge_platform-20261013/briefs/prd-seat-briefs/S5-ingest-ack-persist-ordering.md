## Open choices — RULED above; listed so the trade-offs are visible
- Where does at-least-once live: manual ack after commit, or a bounded in-process queue plus the broker's persistent session with counted loss?
  - Manual ack after the batch commits (aiomqtt manual_ack, bounded max_queued_incoming_messages) — Strongest guarantee; redelivery on restart means the store must be idempotent on (device, ts, metric) which the unnest write already is; throughput bounded by commit latency — long-term: Each new stage (consent, decode) must sit before the ack and be visible in the tick; a year on, the pipeline is a single linear state machine an agent can read in one file
  - Keep ack-on-receipt, bound the queue, count every drop in IngestTick and alert on it — Smaller change; loss is honest but not prevented, and the buffer's eviction order still decides which rows die — long-term: Every future change to buffer, flush or consent must keep the counting correct; the invariant stays distributed across modules

### `fk-f4a810ed984f` — medium — prior — `src/solar_challenge_platform/ingestion/buffer.py::StoreForwardBuffer.flush` — tags h10, h8, h7, comments, kind:missing-invariant — class structural — source hotspot-survey-solar_challenge_platform-20261013
- statement: StoreForwardBuffer.flush writes self._rows[:n] on a daemon thread, then deletes the first len(slice) rows by position. StoreForwardBuffer.offer evicts from the same front on overflow. An offer that interleaves therefore shifts the delete onto rows that were never written, which is silent loss. The buffer has no lock and no notion of an in-flight slice. Safety comes from two places. Subscriber._flush_lock covers _write_pending, which includes the stop's _offer(held). _consume's call to _offer runs on the event loop without the lock, and is safe only by the temporal argument 'admission never runs here during a flush', which _consume's docstring states. The invariant is explained three times (_write_pending, _consume, _offer docstrings), and readers _counts and _report_flush_cycle read buffer state without the lock by design. _received_rows and _persisted_rows are advanced on both the loop and write threads. Three fix commits in one week were about this concurrency: serializing _flush_now, moving writes to daemon threads, and 'the write's thread only writes'.
- proposal (input, not instruction): Give the buffer a take/confirm protocol with immutable batches. StoreForwardBuffer.take(max_rows) returns a frozen Batch (a tuple of rows plus a token) and marks it in flight, and confirm(batch) removes exactly those rows by identity. Eviction never touches an in-flight batch: it evicts the oldest not-in-flight rows and counts them. The buffer owns its own lock, so the guarantee holds for any caller. The write thread receives only the frozen Batch (heuristic 8). Code that dies: Subscriber._flush_lock, the 'held is buffered under the lock too' branch and its docstring, the temporal-safety paragraph in _consume, and positional del-by-length in flush.
